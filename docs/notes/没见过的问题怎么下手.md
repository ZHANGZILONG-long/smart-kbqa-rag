# 没见过的问题怎么下手

> **这份文档解决一个具体的困境**：
>
> 「面试官问我一个没见过的问题，我连别人是怎么解决的都不知道，又怎么深究底层呢？」
>
> 这个困境成立的前提是：**你以为解题的顺序是「先知道别人怎么做 → 再深究底层」。**
> 这个顺序是反的。这份文档就是把正确的顺序拆开给你看。

---

## 一、先把那个顺序纠正过来

### 你的假设是这样的

```
我的假设：
   知道别人怎么做  →  才能深究底层
        ↑
     我卡在这里（连做法都不知道）
```

如果我连「别人怎么判断两个文件是否相同」都不知道，那往下拆底层不就无从下手了吗？

### 实际情况是这样的

```
真实情况：
   把问题归类  →  从类别里调出武器  →  用底层原理判断哪个武器对  →  做法自然就出来了
                     ↑
              （不是回忆，是组合）
```

**老手遇到没见过的问题，他也不知道答案。** 他做的是三件事：

1. **归类**：这是哪一类问题？（判等？去重？限流？）
2. **调武器**：这一类问题的人通常用哪几把武器？
3. **判断**：用底层原理（代价、正确性、复杂度）判断哪把对。

第 3 步**就是**「深究底层」的位置。它不是最后做的事后解释，它是**决策的工具**。

### 关键的认知转换

> **底层原理不是「往下解释用的词典」，是「往上生成方案的引擎」。**

这个区别很具体：

- **当成词典**：我知道唯一索引，所以我解释「为什么这里要用唯一索引」。（事后解释，用不上，因为面试官问的是新问题）
- **当成引擎**：我知道「并发的本质是检查和执行之间有时间窗口」，所以面对任何一个并发写的问题，我都能推导出「需要一个能原子地完成检查和执行的机制」。

**第二种用法，让你在没见过的问题上也能给出答案。** 而且给出来的是推导，不是背诵——面试官一追问就知道差别。

---

## 二、完整的推导演示

现在把面试官那道题从头推一遍。**注意看每一步是怎么从「上一个方案的瓶颈」走到「下一个方案」的。整条链没有一步需要「我以前见过」。**

### 题目原话

> 「如果文件名一样但文件内容不一样，或者前半段一样、后半段不一样，你怎么判断？」

（面试官还提示了一句「不用说完全区分出来，有个大概就行」——这句提示后面会讲。）

---

### 第 0 步：翻译问题，去掉所有技术词

拿到问题先别想技术。先问：**这件事的本质矛盾是什么？**

这道题翻译过来是：

> **我要判断两份数据是不是「同一份」，但两份数据都很大，我不能把它们都完整读一遍。**

矛盾点很清楚：**要判断相等就必须比较，要比较就得接触数据，但数据太大，接触不起。**

这一步很重要。**问题一旦被翻译成「矛盾」，它就从「一道我不知道答案的题」变成了「一个有约束条件的优化问题」。** 后面所有动作都是在这个约束下找路子。

---

### 第 1 步：先想最笨的办法（不能跳过）

最笨的办法是什么？**把两个文件都读完，一个字节一个字节比。**

这个办法**完全正确**，只是慢。

很多人觉得这一步浪费时间，直接跳到答案。**但这一步是后面所有东西的起点**——因为你必须知道「慢在哪」，才知道要优化什么。

**记住这个动作：永远先写暴力解。** 它是基线，也是所有优化的坐标原点。

---

### 第 2 步：找暴力解的瓶颈

暴力解慢在哪？慢在**必须读完整份数据**。

于是问题变成：**能不能不读完整份数据，就做出判断？**

这就是整个推导的第一根杠杆。**问题转型了**：从「怎么比较两份文件」变成「怎么在不读全量的前提下比较」。

---

### 第 3 步：找一个「更小的代表」

既然读全量太贵，那问一句：**有没有什么东西，比文件本身小很多，但能代表它？**

这一问，就把「摘要（哈希）」**推出来了**——不是想起来有这么个东西，是这一问的答案只能是它。

原理很清楚：**用一个固定的、输入相关的短串来代表任意长的数据。** 只要两份数据相同，短串就相同；只要短串不同，数据一定不同。

这里的关键不是「我知道哈希」，是**「我知道我要一个什么样的东西」**——要短、要由内容决定、要变化敏感。哈希恰好满足这三个要求。

---

### 第 4 步：继续找瓶颈

但摘要有个问题：**算摘要本身也要读完整份文件。**

绕了一圈，瓶颈还在「读全量」上。所以继续往上找：**有没有什么东西，比摘要更便宜，甚至不用读内容就能拿到？**

有：**文件大小**。

文件大小存在文件系统的元数据里，**读它不需要碰文件内容**。而且大小不同的两个文件必然不同，一条都不用算。

**所以第一个检查应该是比大小。** 而且它必须排在最前面，因为它最便宜。

---

### 第 5 步：顺着「便宜优先」一路排下去

现在有一个清晰的排序原则了：**从便宜到贵**。

那么排在「大小」和「全量摘要」之间的是什么？→ **只读一小部分内容**。

读哪一部分性价比最高？→ **开头和结尾**。因为很多文件格式的类型标识、长度、元数据都在头部，尾部则常放索引或结束标记。

读多少？→ **几 KB** 就够，因为在这几 KB 里，随便改一个字节都会让哈希变掉。

**于是「抽样比首尾哈希」被推出来了。** 它不是从哪本书上背的，是「找中间档」找出来的。

---

### 第 6 步：换个需求，重新推一次

前面推的是「判断是不是同一个文件」。

但如果需求是**网盘秒传**——那么「知道它们不同」还不够，**还要知道哪里不同**，才能只传那一段。

需求变了，约束变了，重新找瓶颈：**全量摘要只能回答「同/不同」，它把差异信息丢掉了。**

为什么丢掉？→ 因为摘要是**有损压缩**：把任意长的数据压成固定短串，信息必然大幅丢失。**这个损失是它便宜的原因，也是它不够用的原因。**

要保住「哪里不同」，就不能把整份文件压成一个值，得**压成一组值**：把文件切成块，每块一个摘要。

**「分块摘要」被推出来了。** 而且这一步同时把「Merkle 树」也带出来了——如果你还想快速判断「两边哪些块相同」，就会自然想到把这些块摘要组织成一棵树，比较树的分支，不用逐块比。

---

### 第 7 步：新方案带来的新问题

分块了，但怎么切？

最自然的做法是按固定长度切（每 4MB 一块）。**然后立刻发现一个致命的坏情况**：

> 在文件开头插入一个字节，后面所有块的边界全部错位，每一块的摘要都变了。
>
> 结果：这份文件只多了 1 个字节，但**每个块都要重传**。

这是新问题。回到矛盾：**固定切法的问题是「切点由位置决定，不由内容决定」。**

那反过来呢？→ **让切点由内容决定**：扫过数据时算一个滚动哈希，当哈希值满足某个条件时就切一刀。

这样，插入一个字节，**只有它附近的那一刀会移动，后面所有的切点自动对齐**。

**「内容定义分块（CDC）」被推出来了。** 注意：到这里你根本不需要听说过 CDC 这个词——你只需要问「切点为什么错位、怎么让它不错位」。

**这一步是整场演示里最重要的地方。** 因为它证明了：工业界的做法是可以被「从矛盾出发」推出来的。CDC 是结论，不是前提。

---

### 第 8 步：回到面试官那句提示

现在回头看面试官说的「不用说完全区分出来，有个大概就行」。

这句话在说什么？→ 他在**替换约束条件**。

严格判等要求「100% 准确」，那要多贵有多贵（哪怕用了摘要，理论上还有碰撞可能）。而他说「有个大概就行」，等于**把约束从「必须正确」放宽到「错判率低到可接受」**。

约束一放宽，空间立刻打开：布隆过滤器、抽样、概率性结构——这些**不保证正确、但极便宜**的手段全都能用了。

**这是这道题最值钱的一课**：遇到卡住的问题，先问「哪个约束是真的必需的」。**很多难题难，不是因为难，是因为你给自己加了不必要的约束。**

---

### 回头总结这条链

```
问题：判断两份大数据是否相同
  ↓ 翻译成矛盾：比较需要接触数据，数据太大
第 1 步  暴力解：读全文逐字节比          ← 建立基线
  ↓ 瓶颈：必须读全量
第 2 步  找一个更小的代表：摘要（哈希）   ← 用「要什么」反推出「是什么」
  ↓ 瓶颈：算摘要也要读全量
第 3 步  找不用读内容的东西：文件大小      ← 最便宜的先上
  ↓
第 4 步  中间档：抽样比首尾                ← 纯插值，找性价比
  ↓ 需求变了（要知道哪里不同）
第 5 步  分块摘要 → Merkle 树             ← 有损压缩要「分级」而不是「一次性」
  ↓ 瓶颈：固定分块边界漂移
第 6 步  切点由内容决定 → CDC              ← 完全推导出来的，不需要预先知道
  ↓ 最后
第 7 步  用「放宽约束」检查一遍            ← 面试官提示的那个方向
```

**这条链上每一步的驱动力，都是「上一个方案的瓶颈」。** 没有一步是「我想起了某个现成的答案」。

---

### 补一步：量级估算（少了这一步，后面全是猜）

前面那条链里我漏讲了一个动作，但它是**第 2 步和第 3 步之间的必经环节**：

> **在找瓶颈之前，先把维度乘起来。**

**为什么必须算**：因为「瓶颈在哪」这个判断，完全依赖数量级。同样一句「每秒几百条」，乘以「500 人」和乘以「1」是两个宇宙；再乘以「一天」，一个能扛、一个会爆。

**不算，你就只能靠感觉猜，而感觉几乎每次都会指向错的地方。** 人会本能地担心那些「听起来就很大」的东西（比如消息本身有多大），而忽略那些「乘出来才大」的东西（消息数 × 人数 × 时间）。

#### 六步

| 步 | 做什么 | 关键点 |
|---|---|---|
| 1 | 找出会被**乘起来**的维度 | 漏一个维度，结果差几个数量级 |
| 2 | 每个维度取一个数 | 不用精确，同一数量级就够 |
| 3 | 乘 | |
| 4 | 换算成能对比的单位 | 字节、条数、每秒次数、钱 |
| 5 | 和硬件能力对照 | 内存几十 GB、单机 QPS 十万、磁盘几 TB |
| 6 | **问一句：它随时间增长吗** | 增长方式比当前大小更重要 |

第 6 条最容易被忽略，也最致命。

#### 例子（就用后面那道群聊已读的题）

500 人的群，每秒 500 条消息，如果**每条消息给每个读过的人记一笔**：

```
维度：消息数 × 人数 × 时间
     500 条/秒 × 250 人（假设一半人会读）  = 125,000 条/秒
     125,000 × 86,400 秒                  = 108 亿条/天
     108 亿 × 20 字节（两个 ID）           = 216 GB/天（不含索引开销）
```

读出三个结论：

- **写入**：每秒 12.5 万次。单机 Redis 大约十万级 QPS，单机 MySQL 大约一万级——**当天就过载**。
- **空间**：每天涨 216 GB。这就是第 6 条要问的——**它随时间线性增长，永不停止**。这比「现在占多少」严重得多。
- **对比**：换一个把状态压成「每人一个数字」的方案，500 人一共 8 KB；10 万个群也才 800 MB。

**两者的差距是五到六个数量级。** 这种差距不需要精确计算，但**必须把维度乘起来才看得见**。

#### 这个动作你在项目里做过一次

你给问答单独限流到 30 次每分钟，理由是「它最贵」——那次你算对了**成本**。

现在把同样的动作，用到**空间**和**次数**上。同一件事。

## 三、同一个方法，换一道题再走一遍

用上一轮那道「同一个请求点了两次」验一遍，你会看到同样的形状。

```
问题：用户点两次，扣了两次钱
  ↓ 翻译成矛盾：重复一定会发生（网络不可靠），但我只能执行一次
第 1 步  暴力解：加个标记，做过的就不再做了
  ↓ 瓶颈：并发时两个请求同时看标记，都看到「没做过」
         → 检查 和 设置 之间有时间窗口
第 2 步  让检查与设置不可分割（原子）
         → 谁能提供原子？数据库唯一索引 / Redis SETNX / 文件系统的 O_EXCL
         这三个的共同点是：能让「插入」这个动作原子地失败   ← 这就是底层
  ↓ 换一个角度
第 3 步  能不能不依赖去重机制？→ 看操作本身能不能设计成天然幂等
         「把余额设为 100」（PUT 语义）天然幂等，执行几次都一样
         「余额加 100」（累加语义）不行，必须靠第 2 步兜底   ← 这是 HTTP 语义那一层
  ↓ 检查
第 4 步  有没有更重的方案被误用？→ 分布式锁。能用唯一索引解决的，不该上它
```

**看出形状了吗**：暴力解 → 找瓶颈 → 用底层原理找一个能突破瓶颈的机制 → 检查有没有更简单的角度。

**两道题的底层机制完全不同**（一道是哈希，一道是原子性），**但推导的形状一模一样**。这个形状才是你要带走的东西。

## 四、那「别人平时的做法」怎么积累？

上面讲的是「没见过的题怎么推」。但推出来的东西需要校验——**别人是怎么做的，能告诉你「你的推导有没有漏」**。

所以「积累别人的做法」这件事仍然要做。但**做法和你想的不一样**。

### 三个真正有用的来源

**第一，规范文档（RFC、论文、协议标准）。**

它们是「别人怎么做」的原始出处，而且**带论证**。比如想知道 HTTP 为什么定义 PUT 是幂等的，答案就在 RFC 里，而且解释了为什么这么设计。

对比一下：博客只告诉你「PUT 是幂等的」，RFC 告诉你「为什么要保证它幂等、服务端该怎么做、不幂等会怎样」。**前者给你结论，后者给你推理。**

**第二，成熟系统的设计文档和演进史。**

Redis 的过期策略、Kafka 的存储格式、Git 的对象模型、PostgreSQL 的 MVCC——这些系统的设计文档里都有「我们考虑过 A 和 B，为什么选了 B」。

**读演进史比读最佳实践有用十倍。** 因为最佳实践只给你结论，演进史给你**当年的约束条件和取舍过程**。而你要学的恰恰是后者——结论会过时，取舍的方法不会。

**第三，故障复盘（postmortem）。**

别人踩的坑，是「约束条件」最好的教材：当时为什么没看出来、哪个假设错了、加什么机制能防住。

### 一个反面清单

这几类东西**看起来像知识，实际学不到东西**：

- 「XX 的 10 个最佳实践」——只有结论，没有推导，你换一个场景就不会用了。
- 「XX 面试题 100 问」——同上，而且答案常常是结论的堆积。
- 「XX 从入门到精通」——覆盖面广但没有深度，读完还是不会推。

**判断标准很简单**：这份材料有没有告诉你「为什么不那样做」。**有，就是真材料；没有，就是清单。**

## 五、类别表：你的武器库（这是你要补的那一块）

前面说了，推导的第一步是**归类**。所以你需要一张类别清单——**但你要记的不是做法，是类别的名字和矛盾**。

因为做法是无限的、会过时的；**类别是有限的、稳定的**。记住类别的名字，遇到新问题时脑子里能打开对应的抽屉，做法自然就组合出来了。

下面是我整理的后端常见类别。**不要背做法，要记住「这个类别在解决什么矛盾」。**

| # | 类别 | 在解决什么矛盾 | 典型武器（知其意即可） | 共同的取舍轴 |
|---|---|---|---|---|
| 1 | **判等 / 去重** | 比较需要接触数据，但数据太大 | 比便宜特征 → 摘要 → 分块摘要 → 布隆过滤器 | 准确率 ↔ 计算量 ↔ 存储 |
| 2 | **查找 / 定位** | 逐个找太慢 | 有序结构（树 / 跳表）、哈希表、索引 | 查找速度 ↔ 空间 ↔ 写入成本 |
| 3 | **排序 / 定序** | 顺序本身没有意义，但按顺序能加速 | 比较排序、基数排序、按时间戳生成有序 ID | 时间 ↔ 空间（外部排序） |
| 4 | **计数 / 统计** | 要精确统计，但数据量大到数不完 | 精确计数 → 近似计数（HyperLogLog）→ 采样 | 准确率 ↔ 内存 |
| 5 | **缓存** | 重复计算太贵，但结果会变 | 旁路缓存、写透、写回、多级缓存 | 一致性 ↔ 速度 |
| 6 | **限流 / 配额** | 资源有限，但请求无限 | 固定窗口、滑动窗口、令牌桶、漏桶 | 精确度 ↔ 实现复杂度 |
| 7 | **削峰 / 排队** | 瞬时流量远大于处理能力 | 消息队列、缓冲区、请求合并 | 延迟 ↔ 峰值吞吐 |
| 8 | **重试 / 容错** | 网络和依赖会偶尔失败 | 指数退避、抖动、熔断、超时 | 成功率 ↔ 放大故障的风险 |
| 9 | **幂等 / 恰好一次** | 重复一定会发生，但业务只能执行一次 | 幂等键 + 唯一约束、状态机、版本号、乐观锁 | 正确性 ↔ 实现复杂度 |
| 10 | **事务 / 原子性** | 多个操作必须一起成功或一起失败 | 数据库事务、两阶段提交、Saga、补偿 | 一致性 ↔ 可用性 ↔ 性能 |
| 11 | **并发控制 / 锁** | 多个执行者同时改一份数据 | 悲观锁、乐观锁、CAS、无锁结构、单线程化 | 并发度 ↔ 正确性 |
| 12 | **分片 / 切分** | 单机容量和吞吐有上限 | 按范围、按哈希、按业务维度、一致性哈希 | 均衡性 ↔ 扩缩容成本 |
| 13 | **复制 / 一致性** | 一份数据要能被多个地方读到 | 主从、多副本、法定人数、最终一致 | 一致性 ↔ 延迟 ↔ 可用性 |
| 14 | **压缩 / 摘要** | 存储和传输有成本 | 无损压缩、有损压缩、定长摘要、分块摘要 | 体积 ↔ 精度 ↔ 计算量 |
| 15 | **索引** | 数据多，但要快速取子集 | 主键、二级索引、复合索引、倒排索引、向量索引 | 查询速度 ↔ 写入速度 ↔ 空间 |
| 16 | **过滤 / 筛选** | 候选太多，要快速排除大部分 | 预过滤、布隆过滤器、条件下推、位图 | 召回率 ↔ 成本 |
| 17 | **调度 / 定时** | 事情需要在特定时机发生 | 定时轮询、延迟队列、时间轮、优先队列 | 精度 ↔ 资源占用 |
| 18 | **隔离 / 多租户** | 多方共用一套系统，但数据不能互看 | 行级标识、分表、分库、分 collection | 隔离强度 ↔ 成本 |
| 19 | **降级 / 兜底** | 依赖会挂，但主流程要活着 | 开关、默认值、本地缓存兜底、简化路径 | 功能完整度 ↔ 可用性 |
| 20 | **背压 / 流量控制** | 生产速度 > 消费速度 | 队列上限、拒绝策略、拉模式、动态调节 | 不丢数据 ↔ 不雪崩 |
| 21 | **聚合 / 合并** | 多次小操作成本太高 | 批量提交、合并请求、写合并、组提交 | 吞吐 ↔ 单次延迟 |
| 22 | **分治 / 拆分** | 问题太大，一次处理不了 | 递归拆分、MapReduce、分批处理 | 并行度 ↔ 协调成本 |
| 23 | **抽样 / 近似** | 精确答案的代价不可接受 | 随机抽样、蓄水池抽样、概率数据结构 | 准确率 ↔ 成本 |
| 24 | **增量 / 变化检测** | 每次都全量算太贵 | 时间戳、版本号、变更日志（CDC）、脏标记 | 实时性 ↔ 实现复杂度 |
| 25 | **预计算 / 物化** | 实时算来不及 | 物化视图、离线报表、提前算好结果 | 新鲜度 ↔ 查询速度 ↔ 空间 |
| 26 | **异步 / 解耦** | 让请求方等着不合理 | 队列、事件、回调、发布订阅 | 响应速度 ↔ 复杂度 ↔ 一致性 |
| 27 | **状态机 / 生命周期** | 对象有多种状态，非法跳转要拦住 | 显式状态字段 + 合法转移表、事件溯源 | 正确性 ↔ 灵活性 |
| 28 | **归档 / 淘汰** | 数据只增不减会压垮存储 | 分区 + 丢弃分区、TTL、LRU 淘汰、冷热分离 | 保留时长 ↔ 成本 |
| 29 | **隔离故障 / 舱壁** | 一个模块挂了不该拖垮全部 | 线程池隔离、连接池分离、资源配额、熔断 | 可用性 ↔ 资源利用率 |
| 30 | **版本化 / 可回溯** | 需要知道「以前是什么样」 | 版本字段、不可变日志、快照、软删除 | 可追溯性 ↔ 存储成本 |

### 这张表怎么用

**不是背，是归类练习。** 遇到任何问题，先问：

1. 这属于表里的哪一类？（**可能同时属于两三类**，那就组合）
2. 这一类的「矛盾」是什么？我的问题是不是同一个矛盾？
3. 这一类的武器里，哪几把在我的约束下可行？

**归类不上怎么办？** 说明你的表缺一格。**把缺的那一格补上去**——这就是你的类别表在长大。

**同一个问题往往跨好几类。** 比如「秒传」跨了 1（判等）、14（压缩 / 摘要）、24（增量检测）；「权限两个出口」跨了 18（隔离）和 16（过滤）。**真实问题都是组合，所以组合能力才是关键。**

## 六、怎么练：一个每天五分钟的动作

**反向设计。**

步骤：

1. **挑一个你天天用的东西**，别看它的实现。
2. **问自己**：「如果让我从零设计，我会怎么做？」**必须写出暴力解**，再想瓶颈，再想优化。
3. **然后去查它的真实实现。**
4. **对比差异。差异就是别人的经验。**

### 举几个适合练的例子

| 挑什么 | 你会被逼着想清楚什么 |
|---|---|
| Redis 的 key 过期怎么实现的 | 定时扫描 vs 惰性删除、只增不减怎么办（→ 会撞到随机抽样） |
| 登录状态怎么记住的 | 状态放哪儿、怎么撤销、怎么防止被冒用 |
| Git 为什么存快照不存差异 | 空间换时间、内容寻址、DAG |
| MySQL 为什么用 B+ 树不用哈希 | 范围查询、磁盘页、树高 |
| DNS 为什么是分层的 | 集中式为什么不行、缓存与 TTL |
| 队列满了应该丢谁 | 背压策略、公平性 |

**为什么这个练法有效**：它先逼你**推导**，再给你**对照**。推导让你形成引擎，对照让你知道自己的引擎哪里缺零件。

而且它不需要新知识——**你现在的知识就够推**。你之所以觉得自己「什么都不会」，有一部分原因是你从来没试过「先自己推一遍」这个动作。

## 七、把这件事说清楚

回到你最初的那句困惑：

> 「我连平时是怎么做的都不知道，又怎么深究底层呢？」

**这句话里的因果关系是反的。**

不是「知道别人怎么做」让你能深究底层，而是：

**深究底层让你能在不知道别人怎么做的情况下，推出来。**

正因为你有了底层原理，你看到「文件太大不能全读」才会想到「找一个更小的代表」；
正因为你懂原子性，你看到「重复一定会发生」才会想到「让检查与设置变成一件事」。

**「别人平时怎么做」是别人推导的结果，不是你的起点。** 你可以用他们的结论做对照（所以要看 RFC 和演进史），但你的起点应该是**矛盾**。

最后一句，也是这份文档最想让你记住的：

> **面试官问一道你没见过的题，他不是想听你说出正确答案。他是想看你在不知道答案的时候，怎么往下走。**
>
> 因为工作中所有的难题，都是你没见过的。
