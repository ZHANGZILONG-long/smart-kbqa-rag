# 问题排查框架（怎么回答"你遇到过什么问题"）

> 这份文档解决一个具体场景：面试官问"实际工作中遇到过什么问题，你怎么解决的"，你该怎么答。
>
> 它的前提是：**你已经学过的那些计算机基础，真正的用途不是回答八股题，而是给你排查方向。**

---

## 一、先纠正一个误解

面试官问这句话，**不是要听你遇到过多么惊天动地的难题**。他要看的是四件事：

1. 你能不能**观察到具体现象**（而不是含糊地说"就是慢了"）
2. 你能不能**提出假设**（而不是瞎试）
3. 你**知不知道怎么验证**假设
4. 你**懂不懂取舍**（任何方案都有代价）

所以"我没遇到过什么大问题"不是问题——真实工作里 90% 的问题都是琐碎的。**真正的问题是"我遇到了，但说不清是怎么定位的"。**

---

## 二、核心动作：把现象翻译成"哪一类资源出了问题"

这一步就是全部功力所在，也是你那些基础知识的真正用途。

### A 类：慢了

先问一句：**到底在等什么？** 不同的答案，排查方向完全不同。

| 现象 | 可能的原因 | 怎么验证 |
|---|---|---|
| CPU 使用率高，就是慢 | 计算密集、算法差 | 看 CPU 占用、做性能分析 |
| CPU 不高，但响应慢 | 在等磁盘、等网络、等锁 | 看 IO 等待、看是否有锁竞争 |
| 数据库查询慢 | 没走索引、全表扫描、N+1 | `EXPLAIN` 看执行计划、慢查询日志 |
| 偶尔慢、大部分时候正常 | 锁竞争、GC、连接池耗尽 | 看耗时的分布，不是看平均值 |
| 上线后才慢 | 数据量变了 | 对比测试环境和生产的数据量 |

### B 类：错了

| 现象 | 可能的原因 |
|---|---|
| 数据偶尔重复 | 并发竞态（先查再插） |
| 读到的是旧数据 | 缓存和数据库不一致 |
| 部分成功、部分失败 | 事务没有覆盖全部操作 |
| 特定输入才出错 | 边界没处理（空值、超长、特殊字符） |

### C 类：挂了

| 现象 | 可能的原因 |
|---|---|
| 跑一段时间后崩 | 内存泄漏、文件句柄/连接没释放 |
| 流量一高就崩 | 没有限流、没有降级 |
| 依赖方一挂自己也挂 | 调用第三方没设超时、没重试、没熔断 |

**把任何问题先扔进 A/B/C 三个抽屉之一，再往下细分。** 这个动作本身就能让面试官看出你有没有结构。

## 三、三种通用的验证手法

光有假设不够，要能证明。

**1. 对照实验**——只改一个变量，看结果变化

- 加索引前 vs 加索引后
- 加锁前 vs 加锁后
- 带 `select_related` vs 不带

**2. 二分定位**——把链路从中间切开

链路上有很多环节：前端 → Nginx → Django → 数据库。**从中间测一次**，就能判断问题在前半段还是后半段，然后继续往那一半切。

（同理，`git bisect` 是找"哪个提交引入的 bug"的二分法。）

**3. 绕过一层**——临时去掉一个环节，看是否恢复正常

- 绕过 Nginx 直连 Django：**如果正常了，问题就在 Nginx**
- 绕过缓存直连数据库：**如果正常了，问题就在缓存**

这个手法简单，但极其有效。

## 四、你项目里的四个真实问题故事

**你其实已经有素材了，只是没把它们当成"问题故事"来讲。**

### 故事 1：流式输出卡住（网络层）

- **现象**：问答的流式输出不是一点点吐出来，而是卡很久之后一次性全出现
- **假设**：数据在中间某个环节被缓冲了。链路上有 Nginx、gunicorn、Django 三层
- **验证**：绕过 Nginx 直接访问 Django，输出正常 → **问题定位在 Nginx**
- **解决**：Nginx 配 `proxy_buffering off`，让它收到一点就转发一点
- **取舍**：关掉缓冲后 Nginx 的转发开销略增，换来真正的实时性

### 故事 2：上传文档后页面卡住（性能层 - A 类）

- **现象**：上传 PDF 后接口要十几秒才返回，用户一直转圈
- **判断**：这不是 CPU 计算慢，而是**耗时任务堵在请求链路里，占住了 worker**
- **验证**：看上传接口的耗时构成——绝大部分时间花在 PDF 解析和向量生成上，不是网络也不是数据库
- **解决**：拆成 Celery 异步任务，接口立刻返回文档 ID
- **取舍**：用户看不到实时进度 → 用文档的 `status` 字段 + 前端轮询来补

### 故事 3：权限不能只过滤一处（正确性层 - B 类）

- **现象（推演）**：文档列表页按权限过滤了，但问答检索没过滤，普通员工能不能搜到财务文档？
- **分析**：数据的**出口不止一个**——一个是 MySQL 列表查询，一个是 Chroma 向量检索
- **结论**：只堵住一个出口就是漏洞
- **解决**：两处都加过滤，而且用同一套规则（`visible_documents_q` 和 `chroma_access_filter` 保持一致）
- **要点**：这是"权限必须覆盖所有数据出口"的典型体现

### 故事 4：同一份文件传两次（待解决，正好当"改进项"讲）

- **现象**：同一个文件上传两次，磁盘存两份，检索结果里出现重复内容互相挤占名额
- **分析**：系统里**没有任何内容指纹**，无法判断"这个文件已经存在"
- **解决思路**：加 SHA-256 内容哈希 + 数据库唯一索引
- **关键细节**：应用层"先查再插"在并发下不可靠（两个请求同时查到"不存在"、同时插入），**必须靠数据库唯一约束兜底**
- **取舍**：算哈希要读一遍文件，但换来去重和秒传能力

## 五、面试话术模板

**五句话讲完一个问题**：

1. **现象**：我遇到的情况是……
2. **判断**：我判断这不是 X，而是 Y（说清分类依据）
3. **验证**：我用……方式确认了
4. **解决**：我改成了……
5. **代价**：好处是……，代价是……，我用……弥补了

**照着模板把故事 2 说一遍**：

> "文档上传后页面要等十几秒才返回。我判断这不是 CPU 计算慢——因为解析和向量生成主要花在等待上——而是这类耗时任务堵在请求链路里，占住了 gunicorn 的 worker。验证的方式是拆解上传接口的耗时，绝大部分时间在 PDF 解析和 embedding，网络和数据库都不是瓶颈。所以我把它拆成 Celery 异步任务，请求立刻返回文档 ID，前端轮询状态。代价是用户看不到实时进度，我用文档的 status 字段加前端轮询来补。"

这段话里没有一句是八股，但每一句都能看出**你懂请求链路、懂 worker 模型、懂异步的代价**。

## 六、怎么练这个能力

**1. 反向挖自己的项目**

对每一个技术选型都问一句"**如果不用它会怎样**"：

- 去掉 `select_related` 会怎样？→ 每条记录额外查库（N+1）
- 去掉限流会怎样？→ 有人刷接口，服务器被拖垮
- 待审批的文档如果直接进向量库会怎样？→ 未审批的内容被检索到，权限泄漏
- 把 Celery 去掉会怎样？→ 请求超时，worker 占满

**"如果不用它会怎样"，就是问题故事的倒放版本。**

**2. 主动制造故障**

把入门文档里那三个实验亲手跑一遍，然后亲手修好：

- GIL 实验 → 改成多进程，看是否真的变快
- 竞态实验 → 加锁后跑，看结果是否稳定
- 死锁实验 → 按统一顺序拿锁，看是否不再卡

**修复的过程，就是一次完整的排查演练。**

**3. 每次都用五句话写下来**

现象、判断、验证、解决、代价。写在文档里也好，写在纸上也好。**写满十个，这个问题你就不怕了。**

## 七、怎么回答"底层"问题：把框架剥掉

### 面试官的典型批评

> 「不要用 Django 内置的东西回答，这个东西你换 Java 又是另一种解决方案，我问的是底层。」

这句话的潜台词是：**你答的是实现，我要的是原理。**

### 一个判断标准

**如果你的答案里出现了框架名或语言名，就说明还没到底。**

- 「用 Django 的 CSRF token 防重复提交」→ 框架特性，换 Java 就变成 Spring Security 的 CSRF token
- 「给请求一个唯一 ID，用数据库唯一索引去重」→ 任何语言、任何数据库都成立

### 分层法：回答前先在心里过四层

| 层 | 内容 | 面试官要不要 |
|---|---|---|
| 1. 业务规则 | 这个操作应该只发生一次 | 你自己补——显得有业务判断 |
| 2. 协议语义 | HTTP 里哪些方法被定义为幂等 | **要** |
| 3. 存储机制 | 唯一索引、原子操作、CAS、版本号 | **要** |
| 4. 框架实现 | Django 的中间件、Spring 的注解 | 除非他问"你怎么实现的"，否则别主动提 |

**大多数人的问题是从第 4 层开始答。** 而面试官想听的通常是第 2、3 层——因为那才是换任何语言都成立的部分。

### 三个自检问题

回答任何技术问题前，问自己：

1. **这个答案里有框架名吗？** 有，就往下一层问：没有这个框架的时候，这件事是怎么做到的？
2. **换一门语言，这个答案还成立吗？** 不成立，说明你答的是实现不是原理。
3. **这个机制最终依赖什么？** 通常落到三样东西上：**存储的唯一约束、操作的原子性、时间的先后顺序。**

### 练习方法

- 每学一个框架特性，问一句「**没有这个框架的时候，这件事怎么做到的？**」
- 去读标准原文（HTTP、TCP 的 RFC），标准本身就是跨语言的
- 把自己写过的答案里的框架名全部删掉，**看还剩什么**

### 两个例子

| 有人这么答（框架层） | 底层应该这么答 |
|---|---|
| 用 Django 的 `annotate` 做分组统计 | 在数据库层做聚合，避免把全部数据取回应用层 |
| 用 DRF 的 `ScopedRateThrottle` 限流 | 在固定时间窗口内计数，超过阈值就拒绝。实现依赖一个原子自增的计数器 |
| 用 Celery 做异步 | 把耗时任务从请求链路里摘出去，用队列解耦生产者和消费者 |

**右边那一列，换任何语言、任何框架都还成立。**

---

## 最后一句

真实工作里的问题，绝大多数都是 A/B/C 三类里那几个基本模式的组合。你不需要见多识广，你需要的是**分类的习惯**——遇到现象先问"这是慢、是错、还是挂了"，然后顺着三个抽屉往下走。

这个习惯建立起来之后，别人再问"你遇到过什么问题"，你脑子里出现的不再是"我好像没什么可说的"，而是"我有三个可以讲"。
