## 先搞懂最根本的一件事：数据结构到底在解决什么

数据放进计算机，可以有很多种"摆法"。摆法不同，三件事的代价就不同：

- **查找**：我要找某个东西
- **插入**：我要加一个新东西
- **删除**：我要拿走一个东西

**没有一种摆法能让三件事都快。** 数据结构就是"根据你更在乎哪件事，选一种摆法"。

打个比方——图书馆的书怎么摆：

- **按编号排**（这是数组）：你想找 3 号书，直接走到 3 号书架拿出来。但给中间插一本新书，得把后面所有书往后挪。
- **按线索串起来**（这是链表）：插新书很方便，改个线索就行。但你要找第 100 本书，只能沿着线索一本本走过去。

这就是全部的秘密：**每种结构都是"牺牲某件事，换另一件事快"。** 记住这句话，后面每一个名词都好理解了。

## 1. 数组（Array）

**是什么**：一排连续的格子，每个格子有个编号，编号从 0 开始。

**生活类比**：一排储物柜，编号 0、1、2、3、4…… 你要 3 号柜子，直接走过去打开就行，**不需要从 0 号开始一个个看**。

**代码**（Python 里叫 `list`，就是数组的一种实现）：

```python
scores = [85, 92, 78, 90]      # 四个格子，编号 0 到 3

print(scores[0])    # 85   ← 直接跳到 0 号柜
print(scores[3])    # 90   ← 直接跳到 3 号柜，不会因为编号大就变慢
print(len(scores))  # 4
```

**为什么按编号取东西这么快**：因为格子是连着的、大小一样，计算机能直接算出来"0 号柜的地址 + 3 × 每个柜子的大小"就是 3 号柜的地址。这是**一步乘法**，不用找。

**代价是什么**：中间插入和删除很慢。

```python
nums = [1, 2, 3, 4, 5]
nums.insert(0, 0)     # 在开头插一个
print(nums)           # [0, 1, 2, 3, 4, 5]
```

在开头插一个，后面五个元素都要往后挪一格。**这就像往排好的书架中间塞书，后面所有书都得挪。**

**一句话总结**：想**按位置快速取**，用数组。这也是最常用的结构，90% 的场景用它就够了。

**你项目里就在用**：`sources`、`steps` 这些列表，都是数组。

---

## 2. 链表（Linked List）

**是什么**：格子不挨在一起，但每个格子里额外记着"下一个格子在哪"。

**生活类比**：**寻宝游戏**。第一张纸条写着"下一个线索在厨房"，厨房那张写着"下一个在书房"…… 你想找第 5 个线索，只能一个个走过去。

**代码**（手写一个，让你看清"每个格子记着下一个"这件事）：

```python
class Node:
    def __init__(self, value):
        self.value = value      # 这个格子装的东西
        self.next = None        # 下一个格子的位置

# 手工串起来：1 → 2 → 3
a = Node(1)
b = Node(2)
c = Node(3)
a.next = b
b.next = c

# 想找 3，只能从 a 开始一步步走
current = a
while current is not None:
    print(current.value)
    current = current.next
# 输出：1  2  3
```

**为什么插入快**：只要改一下"下一个是谁"。

```python
# 在 a 和 b 之间插入一个新节点 z
z = Node(99)
a.next = z        # 让 a 指向 z
z.next = b        # 让 z 指向 b
# 完事，只改了两个指向，没挪动任何数据
```

**代价是什么**：按位置查找慢。想找第 100 个，只能从第一个开始走 100 步。

**一句话总结**：**频繁在中间插东西、删东西**，用链表；**要按位置快速取**，用数组。

**你大概用过它的亲戚**：Python 的 `collections.deque`，还有浏览器的前进/后退历史（本质是双向链表）。

---

## 3. 栈（Stack）

**是什么**：只能从**一头**进出的容器。**后放进去的先出来**（后进先出）。

**生活类比**：**叠盘子**。你洗完盘子往上摞，要用的时候只能从最上面拿。想拿最底下那个，得先把上面的都拿走。

**代码**：

```python
stack = []
stack.append('第一件事')    # 放进去
stack.append('第二件事')
stack.append('第三件事')

print(stack.pop())   # 第三件事   ← 最后放进去的最先出来
print(stack.pop())   # 第二件事
print(stack.pop())   # 第一件事
```

**什么时候用它**：需要"撤销"、"回退"、"匹配"的场景。

**你天天在用的三个例子**：

1. **Ctrl + Z 撤销**：你每次操作压进栈，撤销就是弹出最近一次。
2. **函数调用**：`f()` 调用 `g()`，`g()` 必须比 `f()` 先结束——这就是栈。程序崩了报的"调用栈"就是它。
3. **括号匹配**：检查 `((()))` 是否配对，遇到 `(` 压栈，遇到 `)` 弹栈，最后栈空就说明配对。

---

## 4. 队列（Queue）

**是什么**：一头进、另一头出。**先进先出**。

**生活类比**：**排队买奶茶**。先来的先买到，后来的排在后面。

**代码**：

```python
from collections import deque

queue = deque()
queue.append('小明')     # 排到队尾
queue.append('小红')
queue.append('小刚')

print(queue.popleft())   # 小明   ← 最先来的最先被处理
print(queue.popleft())   # 小红
```

注意：名字里带个 `popleft`（从左边弹出），和栈的 `pop`（从右边弹出）正好相对。

**什么时候用它**：**任务排队**。有一堆活要干，按顺序一件件干。

**你项目里就在用**：Celery 的 broker 就是一个队列——文档上传后，任务被放进队列，worker 从队头取出来处理。

---

## 5. 哈希表（Hash Table）

**是什么**：不靠位置找，而是**用一个公式，从名字直接算出东西放在哪**。

这是入门里最需要想明白的一个，因为它和你熟悉的东西不一样。

**生活类比**：**酒店前台**。

- 数组是：你报房间号"我要 3 号房"，前台直接指给你（因为你知道号码）
- 哈希表是：你报名字"我要找张三的行李"，前台用一套规则（比如"名字笔画数除以 100 取余数"）算出张三的行李在 47 号柜，然后直接指给你

**关键点：你不是按位置找，而是先用公式把名字变成位置。** 走一次公式就行，不用一个个翻。

**代码**（Python 的 `dict` 就是哈希表）：

```python
phone = {
    '张三': '138-0000-1111',
    '李四': '139-0000-2222',
    '王五': '137-0000-3333',
}

print(phone['李四'])       # 139-0000-2222
# 计算机不是从"张三"开始一个个翻，而是把"李四"扔进一个公式，
# 算出这个值存在哪，直接去拿
```

**为什么快**：不管字典里有一百条还是一百万条，找一条都差不多快。这就是"平均 O(1)"的意思。

**"冲突"是什么**：如果"张三"和"李四"用公式算出来是同一个位置怎么办？

这就是哈希冲突。最常见的解法叫**拉链法**——同一个位置排成一队，先找到位置，再在这队里逐个比一下名字。

```python
# 抽象地演示冲突是怎么处理的
buckets = {
    47: [('张三', '138-0000-1111')],                    # 47 号位置只有张三
    52: [('李四', '139-0000-2222'), ('王五', '137-0000-3333')],  # 52 号位置挂了两个
}
# 找"王五"：先算到 52，再在 52 这一队里比名字
```

**代价是什么**：哈希表**没有顺序**。你不能问它"给我第三大的那个"，也不能问"所有名字在'张'到'李'之间的"。**用"有序性"换来了"极快的查找"。**

**一句话总结**：**按名字（键）快速找东西**，用哈希表。

**你项目里就在用**：`{'username': ..., 'password': ...}` 是哈希表，`AuditLog` 的 `detail` JSON 字段也是。**这个你其实天天都在用。**

## 6. 树（Tree）

**是什么**：数据一层层分叉展开的结构。

**生活类比**：**族谱**、或者**公司组织架构图**（老板 → 三个部门经理 → 每个经理下面的员工）。

**代码**（用嵌套的结构表示一棵树）：

```python
company = {
    '老板': {
        '研发经理': ['小王', '小李'],
        '财务经理': ['小张'],
    }
}
print(company['老板']['研发经理'])   # ['小王', '小李']
```

**最有用的那种树：二叉搜索树**

规则很简单：**每个节点，左边的都比它小，右边的都比它大。**

```python
class TreeNode:
    def __init__(self, value):
        self.value = value
        self.left = None
        self.right = None

root = TreeNode(50)
root.left = TreeNode(30)
root.right = TreeNode(70)
root.left.left = TreeNode(20)
root.left.right = TreeNode(40)
```

```
        50
       /  \
     30    70
    /  \
   20   40
```

现在我要找 40：从 50 开始，40 比 50 小 → 往左；40 比 30 大 → 往右；找到了。

**每比一次就砍掉一半的可能。** 一百万个数据，最多比 20 次就能找到（因为 2²⁰ ≈ 100 万）。这就是"O(log n)"的意思——**数据翻倍，只需要多找一次**。

**为什么这个"砍一半"很了不起**：数组要找 40，得从头一个个看，一百万个数据最坏要看一百万次；二叉搜索树最多看 20 次。

**代价是什么**：树必须保持"平衡"（左右差不多深）。如果你按 20、30、40、50、70 的顺序插进去，树会变成一条直线，退化成链表，就没优势了。所以实际用的树（红黑树、B+ 树）都带**自动平衡**机制。

**一句话总结**：**既要快速查找，又要保持顺序**，用树。

**你天天在用的**：文件系统的目录结构、HTML 的 DOM 树、JSON 的嵌套。还有你项目里的数据库索引——MySQL 底层用的 B+ 树就是树的一种。

## 7. 堆（Heap）

**是什么**：一棵特殊的树，它保证**最上面那个永远是最大（或最小）的**。

**生活类比**：**医院急诊分诊**。不管谁先来，最紧急的病人先看。你要的不是"所有人排好序"，而是"随时能拿出最紧急的那个"。

**代码**（Python 自带 `heapq`）：

```python
import heapq

tasks = [5, 1, 8, 3, 9]
heapq.heapify(tasks)          # 变成堆

print(tasks[0])               # 1，最小的永远在顶上
heapq.heappush(tasks, 0)      # 插一个新的
print(tasks[0])               # 0，新的更小，顶上的变了
print(heapq.heappop(tasks))   # 0，弹出最小的
```

**和排序的区别**：排序是"把所有东西彻底理好"，堆是"只保证最 urgent 的那个能被立刻拿出来"。所以堆更便宜、更适合数据一直在变的情况。

**什么时候用它**：**"排行榜"、"优先级"、"Top 10"**。

**例子**：一亿条数据里找最大的 10 个，用堆只要看一遍就够了，不需要把一亿条全排序。

---

## 8. 图（Graph）

**是什么**：一堆点，加上连接它们的线。

**生活类比**：**地铁线路图**。每个站是一个点，每条线路是一条线。

**代码**：

```python
metro = {
    '人民广场': ['南京东路', '静安寺'],
    '南京东路': ['人民广场', '陆家嘴'],
    '静安寺': ['人民广场'],
    '陆家嘴': ['南京东路'],
}
# 从"人民广场"出发，能直接到哪些站？
print(metro['人民广场'])    # ['南京东路', '静安寺']
```

**什么时候用它**：**距离、连通、依赖、关系**。

- 地图导航找最短路线 → 图的最短路径算法
- 判断两个用户认不认识（社交网络）→ 图的连通性
- 一个任务必须在另一个任务之前完成 → 图的拓扑排序

**你项目里的例子**：Django 启动时，哪个 app 依赖哪个 app，就是一个图。

## 9. 排序（Sorting）

**是什么**：把一堆东西按大小（或时间、字母）理顺。

**为什么它这么重要**：因为**排好序之后，查找会变得极快**。

**关键连接**：数组的查找是 O(n)——一个个看。但如果数组**已经有序**，可以用"二分查找"：

```python
def binary_search(sorted_list, target):
    lo, hi = 0, len(sorted_list) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if sorted_list[mid] == target:
            return mid
        elif sorted_list[mid] < target:
            lo = mid + 1      # 目标在右半边
        else:
            hi = mid - 1      # 目标在左半边
    return -1

data = [1, 3, 5, 7, 9, 11, 13, 15]
print(binary_search(data, 13))    # 6
```

一百万个数据，二分查找最多找 20 次，逐个找最坏找一百万次。**这个巨大差距的前提就是"数据已经排好序"。**

所以排序不是为了好看，是为了**让后续的查找变便宜**。这也是数据库要建索引、要 `ORDER BY` 的原因。

**代码**（Python 内置的排序已经非常快，直接用）：

```python
nums = [5, 2, 9, 1, 7]
print(sorted(nums))              # [1, 2, 5, 7, 9]
print(sorted(nums, reverse=True))  # [9, 7, 5, 2, 1]
```

**你项目里就在用**：`Document.objects.order_by('-created_at')`——按创建时间倒序，这就是排序。

# 第二部分：计算机是怎么工作的

前面讲的是"数据怎么摆"。这一部分讲**这些东西到底跑在什么上**——为什么有时候快、有时候慢，快慢的根源在哪。

---

## 1. 内存（RAM）和硬盘

**是什么**：计算机有两种存东西的地方。

- **硬盘**：大、慢、断电数据还在。像**书柜**。
- **内存**：小、快、断电就清空。像**书桌桌面**。

你在做作业（运行程序）的时候，资料必须在桌面上才能动手；书柜再大，你也得先把书搬到桌上。

**代码感受一下内存的"小"**：

```python
import sys

data = [0] * 10_000_000       # 一千万个零
print(f'这个列表大约占 {sys.getsizeof(data) / 1024 / 1024:.1f} MB 内存')
```

一千万个数字就要几十 MB。如果数据是十亿条，内存根本放不下，只能放硬盘。

**解决了什么后端问题**：

1. **为什么 Redis 快**——它把所有数据放在内存里，不碰硬盘。
2. **为什么服务器重启后缓存就空了**——内存断电清空。
3. **为什么会 OOM（内存不足）被系统杀掉**——桌面放不下那么多东西了。你的 Docker 容器设了内存上限，超了就被杀。
4. **为什么"数据量大要分库分表"**——单机内存和硬盘都有上限。

---

## 2. CPU：只会做最简单动作的超级工人

**是什么**：一块每秒能执行几十亿次简单运算的芯片。它看不懂 Python，只看懂一堆最基础的指令（"把这两个数加起来"、"把结果存到那个位置"）。

**生活类比**：一个**极其听话、速度极快、但只会做最简单动作的工人**。你写的一行 Python，他要拆成几十条最基础的指令才懂。

**代码感受一下"CPU 在干活"**：

```python
import time

def heavy_work():
    total = 0
    for i in range(50_000_000):
        total += i
    return total

start = time.perf_counter()
heavy_work()
print(f'用了 {time.perf_counter() - start:.2f} 秒')
```

跑这段时，你可以打开任务管理器，会看到一个 CPU 核心的使用率飙到 100%——那就是这个工人在埋头干活。

**解决了什么后端问题**：

1. **为什么死循环会把服务器拖垮**——一个 CPU 核心被占满了，跑在它上面的其他任务都得等。
2. **为什么"计算密集"的任务要另开进程/机器**——GPU、多核、分布式计算都是为了让更多工人一起干。
3. **为什么同一个功能，换个写法能快十倍**——不是 CPU 变强了，是你让它少干了活。

---

## 3. 缓存：为什么程序有时能快十倍

**是什么**：CPU 太快了，内存根本跟不上它。所以 CPU 和内存之间加了几层"小而快"的临时存储，叫缓存。

**生活类比**：**厨房里的调料架**。

- 你正在用的盐，放在手边的架子上（**寄存器 / L1 缓存**）——伸手就拿到
- 常用的酱油醋，放在灶台旁边（**L2 / L3 缓存**）——转个身
- 不常用的香料，放在后面的储藏室（**内存**）——走过去拿
- 一整箱备用的，放在仓库里（**硬盘**）——开车去取

**这几层有多快**（量级感受，不用背数字）：

| 位置 | 大概耗时 | 类比 |
|---|---|---|
| L1 缓存 | 1 纳秒 | 伸手 |
| 内存 | 100 纳秒 | 走到隔壁房间 |
| 硬盘 | 10 毫秒 | 开车去仓库 |

**硬盘比内存慢十万倍。** 记住这个数量级，后面所有性能问题都能理解。

**关键概念：局部性**

- **时间局部性**：刚用过的东西，接下来很可能还要用 → 所以留在缓存里
- **空间局部性**：用了一个东西，它旁边的很可能也要用 → 所以一次多拿一点（一次拿 64 字节，叫"缓存行"）

**代码感受一下**：

```python
import numpy as np
import time

n = 2000
a = np.zeros((n, n))

# 方式一：一行一行访问（连续内存）
t = time.perf_counter()
for i in range(n):
    a[i, :] += 1
fast = time.perf_counter() - t

# 方式二：一列一列访问（每次跳很远）
t = time.perf_counter()
for i in range(n):
    a[:, i] += 1
slow = time.perf_counter() - t

print(f'一行行访问 {fast:.3f}s')
print(f'一列列访问 {slow:.3f}s')
print(f'后者慢了 {slow / fast:.1f} 倍')
```

同一块内存、同样 400 万次加法，**一列列访问会慢好几倍**。原因只有一个：CPU 一次把一整块连续内存搬进缓存，横着走每次都用得上，竖着走每次都用不上。

**解决了什么后端问题**：

1. **为什么"批量处理"比"一条条处理"快**——减少来回跑腿的次数。
2. **为什么数据库要"顺序读"而不是"随机读"**——随机读每次都要重新找位置。
3. **为什么 `select_related` 能减少查询次数**——一次把需要的都拿回来。
4. **为什么 Python 的 for 循环比 numpy 慢几百倍**——numpy 在底层连续处理，Python 每条都要"工人亲自出门一趟"。

---

## 4. 磁盘：为什么会"卡"

**是什么**：真正存数据的仓库，断电也在。但取东西要"走过去"，很慢。

**关键区别：顺序读 vs 随机读**

- **顺序读**：像从书里一页页往下读，很快
- **随机读**：像每次都要跳到书里另一页，很慢

机械硬盘要靠磁头移动到指定位置（叫"寻道"，约 10 毫秒）；即使是 SSD，随机访问也比顺序访问慢不少。

**代码感受一下**：

```python
import time
import os

# 顺序写
t = time.perf_counter()
with open('seq_test.bin', 'wb') as f:
    for i in range(2000):
        f.write(b'x' * 4096)
print(f'顺序写 2000 块: {time.perf_counter() - t:.3f}s')

# 随机写：每次跳到文件不同位置
t = time.perf_counter()
with open('rand_test.bin', 'wb') as f:
    f.seek(2000 * 4096)      # 先撑大到同样的尺寸
    f.write(b'x')
    for i in range(2000):
        f.seek(i * 4096)
        f.write(b'y' * 4096)
print(f'随机写 2000 块: {time.perf_counter() - t:.3f}s')

os.remove('seq_test.bin')
os.remove('rand_test.bin')
```

在机械硬盘上差距会非常明显，SSD 上也跑得出来。

**解决了什么后端问题**：

1. **为什么数据库要建索引**——索引让"翻遍整本书"变成"直接翻到那一页"。
2. **为什么数据库写入用"日志 + 顺序追加"**（比如 MySQL 的 redo log）——顺序写比随机写快得多，先把操作顺序记下来，之后再慢慢整理。
3. **为什么大文件上传要分片**——断了可以从断点续传，不用从头再来。
4. **为什么备份要连向量库一起备**——`data/chroma/` 在硬盘上，不备就恢复不了。

---

## 5. 把这一部分串起来

你敲下 `Document.objects.filter(status='ready')`，背后发生了什么：

```
Python 代码
  → 被解释成 CPU 指令（第 2 节）
  → CPU 需要的数据去缓存找（第 3 节），找不到就去内存（第 1 节）
  → 数据库要在硬盘上找数据，尽量走索引减少"跑腿"（第 4 节）
  → 结果再一层层送回
```

**一句话记住这一部分**：程序慢，通常不是 CPU 笨，而是它在**等数据**（等内存、等硬盘、等网络）。优化的本质就是**减少等待**。

# 第三部分：操作系统

这一部分回答的是后端最常遇到的问题：**为什么服务会卡、会挂、会算错。**

---

## 1. 操作系统是什么

**是什么**：夹在硬件和你程序之间的一层**大管家**。它负责分配 CPU 时间、分配内存、管理文件、收发网络数据。你的程序不能直接指挥硬件，都要通过它。

**生活类比**：**餐厅经理**。

- 厨师（CPU）只有几个，但客人（程序）有很多
- 经理决定谁先用灶台、谁先上菜
- 你不能自己冲进厨房炒菜（不能直接操作硬件），必须跟经理说

**代码上你在哪见到它**：你写的 `open()`、`socket()`、`Thread()`，底层都是操作系统提供的功能。Python 只是包装了一下。

**解决了什么后端问题**：

- **为什么一台机器能同时跑数据库、Redis、你的服务和 Celery**——操作系统在它们之间分配资源
- **为什么你的程序"看起来"独占了整台机器**——操作系统做了一层抽象

---

## 2. 进程（Process）

**是什么**：一个**正在运行**的程序。它拥有自己独立的一块内存，别人动不了。程序是菜谱，进程是照着菜谱开工的厨房。

**生活类比**：**一家独立餐厅**。有自己的厨房、自己的员工、自己的账本。隔壁那家餐厅的锅烧了，跟你没关系。

**关键点：进程之间是隔离的。**

```python
import os
import multiprocessing

def worker(name):
    print(f'进程 {name}，它的编号 PID = {os.getpid()}')

# 开三个进程
procs = [multiprocessing.Process(target=worker, args=(f'工人{i}',)) for i in range(3)]
for p in procs:
    p.start()
for p in procs:
    p.join()
```

你会看到三个**不同的 PID**（进程编号）。每个都是独立的"厨房"。

**代码演示隔离**：

```python
import multiprocessing

shared = []

def try_modify():
    shared.append('我改了这个列表')   # 在子进程里改
    print('子进程看到的:', shared)

p = multiprocessing.Process(target=try_modify)
p.start()
p.join()

print('主进程看到的:', shared)   # 空的！子进程改的是它自己的副本
```

子进程改了列表，主进程完全不知道——因为它们是两块独立的内存。

**解决了什么后端问题**：

1. **为什么一个服务崩了，别的服务还能跑**——比如你的 Celery worker 挂了，Django 网站照样能访问。
2. **为什么用多进程能绕开 Python 的 GIL**（下一节讲）——每个进程有自己独立的解释器。
3. **为什么 Docker 的一个容器通常跑一个进程**——隔离是它最大的价值。

---

## 3. 线程（Thread）

**是什么**：进程内部的**分身**。它们共享同一块内存，所以沟通方便，但也容易互相踩到。

**生活类比**：**同一家餐厅里的多个厨师**。他们**共用同一个厨房**——拿调料方便（共享数据快），但两个人同时伸手去拿同一口锅，就会撞上（竞争）。

```python
import threading
import time

def cook(dish):
    print(f'开始做 {dish}')
    time.sleep(1)
    print(f'{dish} 做好了')

threads = [threading.Thread(target=cook, args=(f'菜{i}',)) for i in range(3)]
for t in threads:
    t.start()

print(f'开了 {threading.active_count()} 个线程')
for t in threads:
    t.join()
```

三个厨师同时开工，总共约 1 秒完成（如果是串行就要 3 秒）——因为 `sleep` 的时候他们在"等"，不是在"干活"。

**创建线程比进程便宜得多**：不用重新准备一整个厨房，只要多一个人手。

**代价：会抢东西。** 看下一节的演示。

**解决了什么后端问题**：

1. **一个 HTTP 请求一个线程**——Django 的 `runserver` 就是这样，同时能处理几个请求。
2. **共享数据要加锁**——见第 6 节。
3. **线程数不能无限加**——见第 5 节。

---

## 4. 进程 / 线程 / 协程 + GIL

三个词经常一起出现，这里一次性说清。

| | 是什么 | 类比 | 开销 | 能不能真并行 |
|---|---|---|---|---|
| 进程 | 独立的运行单元 | 独立餐厅 | 大 | 能 |
| 线程 | 进程内的分身 | 同一厨房的厨师 | 中 | 能（但 Python 不能） |
| 协程 | 程序自己管理的"轻量任务" | 一个人同时照看几口锅 | 小 | 不能（但够用） |

**GIL 是什么（Python 特有的坑）**

GIL 全称"全局解释器锁"。简单说：**Python 解释器规定，同一时刻只能有一个线程在执行 Python 代码。**

**代码感受一下**：

```python
import threading
import time

def cpu_work():
    total = 0
    for i in range(20_000_000):
        total += i
    return total

start = time.perf_counter()
cpu_work()
cpu_work()
print(f'串行跑两次: {time.perf_counter() - start:.2f}s')

start = time.perf_counter()
t1 = threading.Thread(target=cpu_work)
t2 = threading.Thread(target=cpu_work)
t1.start(); t2.start()
t1.join(); t2.join()
print(f'两个线程跑: {time.perf_counter() - start:.2f}s')
```

**两个线程并不会快一倍，甚至可能更慢。** 因为 GIL 让它们只能轮流用，还要额外花时间来回切换。这就是"Python 多线程做计算任务没用"的原因。

**但有个重要例外**：当线程在**等**的时候（等网络、等文件、等数据库），GIL 会被释放。所以：

- **计算密集**（大量数学运算）→ 多线程没用，要用**多进程**
- **IO 密集**（大量网络请求、文件读写）→ 多线程**有效**，因为大部分时间在等

**解决了什么后端问题**：

1. **为什么 Celery 用进程不用线程**——文档解析、向量生成是计算密集，进程才能真正并行。
2. **为什么 Django 一个请求一个线程还能扛住**——因为大部分时间在等数据库、等网络。
3. **为什么异步框架（ASGI）能扛更多连接**——协程切换比线程便宜得多。

---

## 5. 上下文切换：为什么线程不是越多越好

**是什么**：CPU 从干一件事切换到干另一件事时，必须先把当前的状态（算到哪了、变量是多少）存起来，再加载另一件事的状态。这个动作叫上下文切换。

**生活类比**：你同时处理三件事，每次切换都要"回忆一下我刚才做到哪了"。**切换本身就要花时间。**

**代价**：线程太多，CPU 大部分时间都在"回忆刚才做到哪了"，而不是真的干活。

```python
import threading
import time

counter = 0
lock = threading.Lock()

def work():
    global counter
    for _ in range(50_000):
        with lock:
            counter += 1

for thread_count in [1, 5, 20, 100]:
    counter = 0
    threads = [threading.Thread(target=work) for _ in range(thread_count)]
    start = time.perf_counter()
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    print(f'{thread_count:>3} 个线程: {time.perf_counter() - start:.3f}s')
```

线程数从 1 涨到 100，**总耗时不会变快，反而越来越慢**——多出来的时间全花在争锁和切换上了。

**解决了什么后端问题**：

1. **为什么 gunicorn 的 worker 数不是越大越好**——经验值是 CPU 核数 × 2 + 1，再多就是浪费。
2. **为什么数据库连接池要设上限**——连接太多，切换的成本超过干活的收益。
3. **为什么监控里"CPU 使用率高"不一定是好事**——可能都花在切换上了。

---

## 6. 锁和并发问题：为什么会算错

**问题**：两个线程同时读一个数、各自加 1、各自写回去，结果只加了 1 而不是 2。

**生活类比**：**两个人同时看同一个账户余额（都是 100 元），各自往里存 50 元，各自把结果写回去。** 最后账上是 150 而不是 200——因为后写的人覆盖了前一个人的结果。

**代码重现这个 bug**：

```python
import threading

counter = 0

def add_many():
    global counter
    for _ in range(200_000):
        counter += 1        # 这一行其实分成「读 → 加 → 写」三步

threads = [threading.Thread(target=add_many) for _ in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(f'期望 1000000，实际 {counter}')
```

**每次运行结果都不一样，而且总是小于 100 万。** 多跑几次看看。

**怎么解决：加锁**。锁保证同一时刻只有一个人能进这段代码。

```python
import threading

counter = 0
lock = threading.Lock()

def add_many():
    global counter
    for _ in range(200_000):
        with lock:          # 一次只放一个人进来
            counter += 1

threads = [threading.Thread(target=add_many) for _ in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(f'结果 {counter}')     # 稳定 1000000
```

**死锁是什么**：两个人都拿着对方需要的东西，互相等，永远等下去。

**生活类比**：两人在窄巷里相遇，你要我先退、我要你先退，结果谁都不动。

**代码**：

```python
import threading
import time

lock_a = threading.Lock()
lock_b = threading.Lock()

def person_one():
    with lock_a:
        time.sleep(0.1)
        print('甲：我拿着 A，等 B')
        with lock_b:            # 永远等不到，因为乙拿着 B
            print('甲：拿到了')

def person_two():
    with lock_b:
        time.sleep(0.1)
        print('乙：我拿着 B，等 A')
        with lock_a:            # 永远等不到
            print('乙：拿到了')

t1 = threading.Thread(target=person_one)
t2 = threading.Thread(target=person_two)
t1.start(); t2.start()
t1.join(timeout=2); t2.join(timeout=2)
print('卡住了 —— 这就是死锁')
```

**避免死锁的实用办法**：约定所有人**按同一个顺序**拿锁（比如都先拿 A 再拿 B）。

**解决了什么后端问题**：

1. **为什么秒杀会超卖**——两个请求同时读到"库存 1"，都以为还能卖。解决办法：数据库加锁、或 `UPDATE ... WHERE stock > 0`（把判断和修改合成一个原子动作）。
2. **为什么需要数据库事务**——把多个操作打包成"要么全成、要么全不成"。
3. **为什么"先查再插"不可靠**——两个请求同时查到"不存在"，同时插入，就有两条重复数据了。**必须靠数据库的唯一索引兜底**（这就是秒传那个问题的答案）。

## 7. 虚拟内存：操作系统最大的一个"骗局"

**是什么**：每个程序都以为自己独占了一大片连续内存，其实物理内存是有限的、是被很多程序共用的。操作系统在中间做了一层映射，让每个程序都"看到"一份自己独立的地址空间。

**生活类比**：**酒店房卡**。每个客人都觉得"我的房间号是 301，这层楼就我住"，其实 301 这个号码在别的楼层、别的分店都可能有。是前台（操作系统）在帮大家做映射，各不相干。

**好处**：

1. **隔离**：A 程序写坏了自己的内存，不会影响 B 程序
2. **能用超过物理内存的空间**：暂时不用的部分可以挪到硬盘上（这会让系统变慢，就是"卡"的感觉）
3. **简化编程**：你不用关心内存里哪些位置被占了，操作系统替你安排

**解决了什么后端问题**：

1. **为什么两个服务的内存不会互相篡改**——虚拟内存提供的隔离。
2. **为什么会"内存不足"（OOM）**——物理内存真的用完了。
3. **为什么服务器"swap 变高"就要报警**——数据被挤到硬盘上了，速度会掉到地板上。

---

## 8. 文件系统：删文件为什么那么快

**是什么**：硬盘上本来只有一堆二进制数据，文件系统给它加上了"目录"、"文件名"、"这块数据属于哪个文件"这些组织信息。

**生活类比**：**图书馆的检索卡片**。书还在架上，卡片只是告诉你"编号 J-203 的书在第三排"。**撕掉卡片不等于烧掉书。**

**代码**：

```python
import os
import time

# 建一个大文件
with open('big_test.bin', 'wb') as f:
    f.write(b'0' * 100_000_000)      # 100MB

size = os.path.getsize('big_test.bin') / 1024 / 1024
print(f'文件大小 {size:.0f} MB')

start = time.perf_counter()
os.remove('big_test.bin')
print(f'删除用了 {time.perf_counter() - start:.4f} 秒')
```

100MB 的文件，删除几乎瞬间完成——**因为只是把"目录里那条记录"去掉了**，数据本身还躺在硬盘上，直到被新数据覆盖。这也是为什么删除的文件有时还能被恢复。

**解决了什么后端问题**：

1. **为什么删除大文件是瞬间的**——只删记录，不擦数据。
2. **为什么"删除"后磁盘空间不一定立刻归还**——有些系统是延迟回收的。
3. **为什么备份要覆盖"文件 + 数据库 + 向量库"三处**——它们是三种不同的存储方式，缺一个就恢复不全。
4. **为什么日志要定期清理**——`logs/app.jsonl` 会一直变大。

---

## 9. IO 模型：为什么有的服务器能扛住上万个连接

**问题**：程序要读网络数据，但对方还没发过来。这段"等"的时间，程序该怎么过？

**生活类比**：**去餐厅取餐的三种方式**。

- **阻塞式**：站在窗口一直等，菜好了拿走。**但等你的时候，你什么都干不了。**
- **非阻塞式**：每 10 秒去窗口问一次"好了吗"。**能干活，但问得很累。**
- **多路复用（事件驱动）**：你跟前台说"谁的菜好了叫我一声"。然后你就坐着干别的事，**谁好了前台通知谁**。

**为什么这个区别是天大的事**：

- 传统方式：一个连接一个线程/进程去等。10000 个连接就要 10000 个线程——**光切换就累死了**。
- 多路复用：一个线程就能照看几万个连接，谁的菜好了处理谁。

**这就是 Nginx 和 Redis 快的根本原因**——它们都用事件驱动，用很少的线程处理海量连接。

**代码感受一下**（一个线程同时照看多个连接）：

```python
import selectors
import socket

sel = selectors.DefaultSelector()

def accept(sock):
    conn, addr = sock.accept()
    print(f'新连接来自 {addr}')
    conn.setblocking(False)
    sel.register(conn, selectors.EVENT_READ, read)

def read(conn):
    data = conn.recv(1024)
    if data:
        conn.send(b'echo: ' + data)
    else:
        sel.unregister(conn)
        conn.close()

server = socket.socket()
server.bind(('127.0.0.1', 9000))
server.listen()
server.setblocking(False)
sel.register(server, selectors.EVENT_READ, accept)

print('服务器已启动，监听 9000 端口')
```

这个服务器**只用一个线程**就能同时处理很多连接。对比一下"一个连接一个线程"的写法，你就明白差距在哪。

**解决了什么后端问题**：

1. **为什么 Nginx 能放在 Django 前面扛流量**——它用事件驱动处理静态资源和转发，效率高得多。
2. **为什么客户端请求要加超时**——否则被一个慢请求永久占住一个连接/线程。
3. **为什么你的 SSE 流式接口要小心**——一条长连接会一直占住一个 worker，并发一高就满了。

## 10. 从操作系统看你自己的项目

| 项目里的东西 | 对应操作系统的什么概念 |
|---|---|
| Django `runserver`（一个请求一个线程） | 线程 + 阻塞 IO |
| Celery worker（独立进程） | 进程（绕开 GIL，能真并行） |
| Windows 上 `celery -P solo` | Windows 没有 `fork`，用不了默认的进程池 |

# 第四部分：网络

这一部分回答：**数据是怎么从你的电脑跑到服务器的，中间为什么会出问题。**

---

## 1. 敲下网址到页面出现，发生了什么

先是全流程，后面逐个解释。你在浏览器输入 `https://www.baidu.com` 并回车：

1. **浏览器问 DNS**：`www.baidu.com` 的 IP 地址是多少？
2. **DNS 回答**：`13.215.xxx.xxx`
3. **浏览器和这个 IP 建立连接**（TCP 三次握手）
4. **浏览器发出 HTTP 请求**："请给我首页"
5. **服务器处理并返回 HTTP 响应**（一堆 HTML）
6. **浏览器渲染页面**

**关键认知**：你输的是**名字**，但网络里只认**地址**。中间所有的复杂流程，都是为了把这个名字翻译成地址、再把数据可靠地送过去。

**解决了什么后端问题**：

- **为什么接口会超时**——上面任何一步都可能慢或失败，尤其是第 3 步和第 4 步
- **为什么调试问题要先分清是"网络不通"还是"服务报错"**——这两类问题的排查方向完全不同

---

## 2. IP 地址和 DNS

**IP 地址是什么**：网络里每台机器的**门牌号**，比如 `192.168.1.5`。

**生活类比**：你要给朋友寄快递，必须写门牌号。但门牌号不好记，所以你还存了"朋友家"这个名字。

**DNS 是什么**：一本**电话簿**。你说"百度"，它告诉你号码是多少。

**代码**（需要联网）：

```python
import socket

# 域名 → IP
ip = socket.gethostbyname('www.baidu.com')
print(f'www.baidu.com 的 IP 是 {ip}')
```

**几个要理解的细节**：

- **DNS 结果会被缓存**（浏览器、操作系统、运营商都会缓存），所以改域名指向后不是立刻生效
- **一个域名可以对应多个 IP**（这就是负载均衡和 CDN 的基础）
- **CDN 的原理**：根据你所在的位置，DNS 返回离你最近的服务器 IP

**解决了什么后端问题**：

1. **为什么静态资源要放 CDN**——用户就近取，不走你的服务器。
2. **为什么配 Nginx 要写 `server_name`**——一个 IP 上可能跑很多个站点，靠域名区分。
3. **为什么换服务器 IP 后要等一段时间才生效**——DNS 缓存还没过期。

---

## 3. TCP：为什么数据不会丢

**问题**：网络传输不可靠——数据包可能丢失、可能乱序、可能重复。但你上传文档、提交表单，结果必须是对的。

**TCP 做的就是这件事**：把数据切成小包发出去，然后**在接收方确认收到**，没确认的就重发，乱序的重新排好。

**生活类比**：**寄挂号信**。

- 普通信件（UDP）：扔进邮筒就完事，到不到不知道
- 挂号信（TCP）：要签收，没收到就一直催

**三次握手（建立连接）**：就像打电话的开场白

```
你：喂，能听到吗？           （我想连你）
对方：能听到，你能听到我吗？  （我收到了，你能收到我吗？）
你：能听到。                （我也收到了，开始聊吧）
```

**为什么是三次，不是两次**：两次的话，服务端无法确认"客户端能收到我的消息"。第三次确认了这一点，双方才都确信**双向通道都通**。

**四次挥手（断开连接）**：为什么比握手多一次？

因为 TCP 是双向的，我说完了不代表你也说完了。所以"我说完了"和"我同意结束"要分开发。

**代码感受一下握手的时间成本**（需要联网）：

```python
import socket
import time

ip = socket.gethostbyname('www.baidu.com')

start = time.perf_counter()
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect((ip, 80))       # 这一行就完成了三次握手
print(f'建立连接用了 {(time.perf_counter() - start) * 1000:.0f} 毫秒')
print(f'这次连接的本地端口是 {s.getsockname()[1]}')
s.close()
```

**关键认知**：**每次建立连接都要花时间（至少一个往返）**。所以——

**连接复用（keep-alive）**：连接建好后就别急着关，下一个请求接着用。

**代码对比**：

```python
import requests
import time

# 不复用：每次都要重新握手
start = time.perf_counter()
for _ in range(5):
    requests.get('https://www.baidu.com')
print(f'不复用连接: {time.perf_counter() - start:.2f}s')

# 复用：用同一个 session
start = time.perf_counter()
session = requests.Session()
for _ in range(5):
    session.get('https://www.baidu.com')
print(f'复用连接:   {time.perf_counter() - start:.2f}s')
```

复用会明显更快，省下的就是反复握手的时间。

**解决了什么后端问题**：

1. **为什么数据库连接要用"连接池"**——同一个道理：建立连接很贵，复用才划算。
2. **为什么一次页面加载不要发太多请求**——每个新连接都有握手成本。
3. **为什么负载均衡要支持长连接**——否则每来一个请求都要重新建立后端连接。

## 4. HTTP：浏览器和服务器的对话格式

**是什么**：一套固定的"填表格"格式。浏览器填一张表发给服务器，服务器填一张表回给你。

**请求长这样**（你项目里的接口也是这样）：

```
POST /api/qa/ask/ HTTP/1.1          ← 方法 + 路径 + 版本
Host: 127.0.0.1:8000                ← 发给谁
Authorization: Bearer eyJhbGc...     ← 我是谁（JWT）
Content-Type: application/json       ← 我发的是 JSON

{"question": "请假流程是什么？"}      ← 真正的内容
```

**响应长这样**：

```
HTTP/1.1 200 OK                     ← 状态码
Content-Type: application/json

{"answer": "请假需要主管审批...", "sources": [...]}
```

**状态码就是服务器给你的"表情"**：

| 状态码 | 意思 | 你项目里什么时候出现 |
|---|---|---|
| 200 | 成功 | 正常返回 |
| 201 | 创建成功 | 上传文档成功 |
| 204 | 成功但没内容 | 删除文档成功 |
| 301 / 302 | 跳转 | 访问 `/` 跳登录页 |
| 400 | 你发的参数有问题 | 提交的数据格式不对 |
| 401 | 你没登录 | token 过期 |
| 403 | 你登录了但没权限 | 普通员工上传文档 |
| 404 | 找不到 | 别人的会话 ID |
| 429 | 请求太频繁 | 触发限流 |
| 500 | 服务器自己崩了 | 代码有 bug |

**分不清 401 和 403 的人很多**：401 是"你没证明你是谁"，403 是"我知道你是谁，但你不能干这个"。你项目里两者都用到了。

**代码**：

```python
import requests

r = requests.get('https://www.baidu.com')
print(f'状态码: {r.status_code}')
print(f'响应头里的服务器: {r.headers.get("Server")}')
print(f'返回内容大小: {len(r.content)} 字节')
```

**解决了什么后端问题**：

1. **为什么接口要区分状态码**——前端根据状态码决定"跳登录页"还是"提示无权限"。
2. **为什么会出现"跨域"报错**——浏览器出于安全，默认不允许一个网站随便调另一个网站的接口，需要服务端明确说"我允许"。
3. **为什么 token 过期要让前端知道**——返回 401，前端才有机会去刷新 token 或跳登录。

## 5. HTTPS：给数据加密

**HTTP 的问题**：数据在网络上是明文传输的。中间任何一个环节（路由器、运营商、公共 WiFi）都能看到内容，甚至篡改。

**HTTPS 做的事**：给数据加个信封，只有你和服务器能拆开。

**生活类比**：

- HTTP = **明信片**，一路传过去，谁都能看
- HTTPS = **带密码锁的盒子**，只有收件人有钥匙

**关键点（不用深究原理，知道结论就行）**：

- 用的是**证书**来确认"对面真的是这家网站"，不是冒充的
- 你项目里配置了 `SECURE_*` 那一堆设置，就是让 Django 在生产环境走 HTTPS
- **本地开发用 HTTP 没问题**，因为数据没离开你的电脑

**解决了什么后端问题**：

1. **为什么生产环境必须上 HTTPS**——否则用户密码在网络上是明文。
2. **为什么 Cookie 要加 `Secure` 标记**——只在 HTTPS 下发送，防止被窃取。
3. **为什么部署要用 Nginx 配证书**——`deploy/certs/` 那目录就是放证书的。

## 6. 从网络看你自己的项目

| 项目里的设计 | 对应的网络知识 |
|---|---|
| JWT 放在 `Authorization` 头里 | HTTP 请求头 |
| 401 跳登录、403 提示无权限 | 状态码的语义 |
| 登录接口限流 20 次/分钟 | 防撞库 = 防暴力破解 |
| 问答接口限流 30 次/分钟 | 网络层的成本控制（每次都要调大模型，烧钱） |
| SSE 流式输出 | HTTP 的"边算边发"，要配 `proxy_buffering off` |
| Nginx 反代 Django | 反向代理 + 负载均衡 |
| 静态文件由 Nginx 直接返回 | 减少请求在应用层的开销 |
| 数据库连接池 | 复用连接，省掉反复握手 |
| 客户端请求要设超时 | 网络不可靠，不能无限等 |

**一句话记住这部分**：网络的核心矛盾是**不确定**——不知道数据到没到、不知道对面是谁、不知道快还是慢。TCP 解决"可靠"，HTTPS 解决"安全"，连接复用解决"快"。
