# 问题模式库

> 这份文档回答一个具体问题：**"科班和非科班、有水平的人和应届生，差距到底是什么？"**
>
> 答案的关键是：那个差距**不是一种模糊的天赋**，而是一个**有限的、可以打勾的清单**。

---

## 一、"科班"到底给了什么

诚实地说，科班教育真正给的是三样东西：

### 1. 一套共同词汇

说"这里存在竞态"、"这个接口要保证幂等"、"这是典型的 N+1"——同行立刻懂你在说什么。

**词汇的价值不在于显得专业，在于它能压缩沟通成本。** 没有词汇的人描述同一个问题，要说五句话；有词汇的人说一个词。

### 2. 一个模式库

看到某个形状的问题，脑子里立刻跳出"这有个名字叫 X，标准解法是 Y，代价是 Z"。

比如：看到"数据偶尔重复"→ 想到竞态 → 想到唯一索引；看到"缓存和库对不上"→ 想到失效策略。

### 3. 一张查询地图

不知道细节，但知道"这个问题属于哪个领域、该去看什么"。

不记得 LRU 怎么实现，但知道"这是缓存淘汰策略，去看操作系统页面置换那章"。

**非科班常见的缺口是第 1 和第 2 条。** 但关键是下面这件事。

---

## 二、为什么这个差距被高估了

三个事实：

**第一，大多数科班生也没把第 2 条用起来。**

考试能认出"B+ 树"、能背出"死锁四个条件"，但面对真实系统里的"接口偶尔变慢"，同样不知道从哪下手。**这不是科班的特权，这是所有人的普遍状态。**

**第二，"有水平的人"的共同点不是学历。**

他们共同的是：**"观察现象 → 归类 → 验证 → 修正"这个循环做了很多遍**。这个循环主要是在工作里积累的，学校给不了。

一个人做实习三个月，可能比读四年书积累的模式更多。

**第三，这个差距是可以量化的。**

科班四年涉及的核心概念，认真数一遍大约五十个；真实工作里常见的问题模式，大约三十种。**这是一个有限集合。** 有限集合意味着：可以列出来、可以打勾、可以补完。

**把它神秘化，是阻止自己进步最快的方式。**

## 三、问题模式清单

把"我不行"这种模糊感受，换成一张能打勾的表。下面是 21 种真实工作里最常见的问题模式。

### A 类：慢了

| 现象 | 常见原因 | 怎么验证 | 涉及的基础 |
|---|---|---|---|
| 单条查询慢 | 没走索引，全表扫描 | `EXPLAIN` 看是 `SCAN` 还是 `SEARCH` | 第二部分：磁盘 IO |
| 列表页慢 | N+1 查询 | 数一下这个接口发了几条 SQL | 网络往返成本 |
| 上线后才慢 | 数据量变了 | 对比测试环境和生产的行数 | 复杂度分析 |
| 偶尔慢，大多正常 | 锁竞争、连接池耗尽 | 看耗时的**分布**，不看平均值 | 操作系统：锁 |
| CPU 使用率高 | 计算密集、算法差 | 找到热点函数 | CPU |
| CPU 不高但很慢 | 在等 IO、等网络、等锁 | 看等待时间占多少 | IO 模型 |
| 遍历数据慢 | 缓存不友好 | 对比顺序访问和随机访问 | 缓存行 |
| 批量操作慢 | 一条条处理，来回跑腿太多 | 改成批量 | 局部性 |

### B 类：错了

| 现象 | 常见原因 | 怎么验证 | 涉及的基础 |
|---|---|---|---|
| 数据偶尔重复 | 并发竞态（先查再插） | 多线程复现；靠唯一索引兜底 | 操作系统：锁与原子性 |
| 读到旧数据 | 缓存与数据库不一致 | 对比两边的值 | 缓存一致性 |
| 部分成功、部分失败 | 事务没覆盖全部操作 | 检查是否都在同一个事务里 | 数据库：原子性 |
| 重试后出现重复 | 接口不幂等 | 重复调用同一请求看结果 | 幂等设计 |
| 权限泄漏 | 数据出口漏了一个 | **数清一共有几个出口** | 你的项目：MySQL + Chroma |
| 特定输入才出错 | 边界没处理 | 空值、超长、特殊字符 | — |

### C 类：挂了

| 现象 | 常见原因 | 怎么验证 | 涉及的基础 |
|---|---|---|---|
| 跑一段时间就崩 | 内存泄漏、句柄/连接没释放 | 观察内存和连接数随时间变化 | 虚拟内存、文件描述符 |
| 流量一高就崩 | 没有限流、没有降级 | 压测 | 资源有限性 |
| 依赖方挂了跟着挂 | 没设超时、没重试、没熔断 | 断开依赖看表现 | 网络不可靠 |
| 任务越积越多 | 消费速度 < 生产速度 | 看队列长度 | 队列 |
| 磁盘写满 | 日志没轮转 | 看磁盘占用 | 文件系统 |

## 四、怎么建立自己的模式库

**1. 读别人的故障复盘**

搜"postmortem"或"故障复盘"，看别人怎么从现象追到根因。**你不需要亲身踩过每个坑，但可以读过每个坑。**

**2. 亲手跑实验**

入门文档里那三个并发实验（GIL、竞态、死锁），跑一遍再修一遍。**修复的过程就是一次完整的排查演练。**

**3. 反向挖自己的项目**

对每个技术选型问"**如果不用它会怎样**"：

- 去掉 `select_related` → N+1
- 去掉限流 → 被刷爆
- 去掉唯一索引 → 并发下重复
- 待审批文档直接进向量库 → 权限泄漏

**问出来的答案，就是问题故事的倒放版本。**

**4. 每个模式写成一句话**

> 什么现象 → 可能是什么原因 → 用什么手段验证

写满十条，你回答"遇到过什么问题"时就不慌了；写满三十条，你会开始觉得"也就那几类"。

---

## 五、最后

你现在的位置其实很好：**你已经知道了名词，也就是有了词汇表；你缺的是"这个名词在什么场景下会用到"。**

而"场景"这件事，靠的不是再多学一门框架，是**把已经知道的名词，往真实问题上挂**。

你刚才自己得出的那个结论——"把问题分解成底层问题去想怎么解决"——就是这套方法的全部核心。你没有比别人晚开始，你只是第一次知道了该往哪个方向练。
