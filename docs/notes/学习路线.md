## 总览：先记住这张图

```
浏览器 (templates/*.html)
   │  JWT: Authorization: Bearer xxx
   ▼
config/urls.py  ──►  apps/*/urls.py  ──►  apps/*/views.py
                                              │
                    ┌─────────────────────────┼──────────────────────┐
                    ▼                         ▼                      ▼
              apps/*/models.py         documents/tasks.py        qa/graph.py
              (MySQL 表)               (Celery 异步)             (LangGraph RAG)
                                              │                      │
                                              ▼                      ▼
                                     documents/services/      Chroma 向量库
                                     parser→chunk→vector     + DeepSeek LLM
                                              │
                                              ▼
                                        common/audit.py（审计）
                                        common/views.py（健康检查）
```

一句话：**HTTP 进来 → View 校验权限 → 模型读写 / 异步任务 / RAG → 返回 JSON**。

多轮问答的记忆由 `apps/qa/memory.py` 统一管理（滑动窗口 + 滚动摘要 + 字符预算），在 `qa/graph.py` 的改写与生成节点注入。

## 阶段 1：请求从哪进来（1 小时）

### 1.1 读 `manage.py`

**讲解**：命令行入口。只有两件事：
- `os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'config.settings')` → 告诉 Django 去哪找配置
- `execute_from_command_line(sys.argv)` → 把你敲的 `runserver` / `migrate` 交出去执行

**自测**：为什么所有 Django 命令都要经过这个文件？

### 1.2 读 `config/settings.py`

这是全项目最长的文件，按块读，不要通读：

| 配置块 | 你要能说出 |
|--------|-----------|
| `INSTALLED_APPS` | 启用了 accounts/documents/qa/common 四个业务 app |
| `AUTH_USER_MODEL` | 用自定义 `accounts.User`，不是 Django 默认表 |
| `MIDDLEWARE` | 请求从上到下过中间件：安全 → CORS → Session → CSRF → 鉴权 |
| `DATABASES` | 生产 MySQL；`USE_SQLITE` 或跑 test 时用 SQLite |
| `REST_FRAMEWORK` | JWT 认证、默认必须登录、分页 20 条、限流速率 |
| `SIMPLE_JWT` | access 60 分钟 / refresh 7 天，开旋转和拉黑 |
| `CACHES` | Redis；测试用内存缓存 |
| `CELERY_*` | broker=Redis，超时 30 分钟，acks_late |
| `CHROMA_*`/`EMBEDDING_*`/`DEEPSEEK_*` | 向量库与模型参数 |
| `MEMORY_*` | 多轮记忆：窗口轮数、历史字符预算、单条长度上限、摘要上限 |
| `LOGGING` | 自定义 `JsonFormatter`，日志写到 `logs/app.jsonl` |
| `SECURE_*` | 只在 `DEBUG=False` 时启用 HTTPS/Cookie 安全 |

**面试点**：为什么配置要放 `.env` 而不是写死？→ 密钥不入 Git，环境间可切换（开发/测试/生产）。

### 1.3 读 `config/urls.py`

**讲解**：总路由表。分三类：
- `/admin/` → Django 后台
- `/api/xxx/` → 各 app 的 API（认证、文档、问答、健康检查）
- `/login/` `/qa/` `/upload/` 等 → 直接返回 HTML 模板（`TemplateView`）
- `/` → 重定向到登录页

**自测**：`/api/qa/ask/` 这个 URL，最终落到哪个 View？

### 1.4 读 `config/wsgi.py`、`config/asgi.py`、`config/celery.py`、`config/__init__.py`

| 文件 | 作用 |
|------|------|
| `wsgi.py` | 同步部署入口，gunicorn 用它（`config.wsgi:application`） |
| `asgi.py` | 异步协议入口，本项目没重度用 |
| `celery.py` | 创建 Celery 应用、从 settings 读配置、自动发现 `@shared_task` |
| `__init__.py` | 导入 celery_app，保证 Django 启动时 Celery 也加载 |

**面试点**：Celery 为什么单独一个文件？→ worker 进程不跑 HTTP，只跑任务，需要用同一套 Django 配置。

**阶段 1 过关标志**：你能画出「URL → View」的映射，并说出 settings 里限流配置长什么样。

## 阶段 3：文档入库（3 小时，最能体现工程能力）

### 3.1 读 `apps/documents/models.py`

**讲解**：`Document` 是个**状态机**：

```
部门管理员上传 → pending_approval
                    │ 总管审批
                    ▼
                 pending → processing → ready
                                     ↘ failed
                    │ 总管驳回
                    ▼
                 rejected
```

- `Visibility`：public（全员）/ department（部门）
- `reviewed_by` / `reviewed_at` / `review_note`：审批痕迹
- `DocumentChunk`：分块内容在 MySQL 的备份，`chroma_id` 关联向量库那条

**为什么 `upload_to` 用 uuid**：避免同名文件互相覆盖，也防止用户文件名带路径。

### 3.2 读 `apps/documents/permissions.py`（面试必考）

**讲解**：全部是纯函数，不依赖 HTTP：

| 函数 | 一句话 |
|------|--------|
| `visible_documents_q(user)` | 返回一个 `Q` 对象，给 `Document.objects.filter()` 用 |
| `can_view_document` | 单条能不能看 |
| `can_upload_document` | 只有管理员 |
| `can_delete_document` | 总管全部；部门管理员限本部门/自己上传 |
| `can_approve_document` | **只有总管**，且状态必须是待审批 |
| `chroma_access_filter(user)` | 生成 Chroma 的 `where` 条件 |

**核心考点**：为什么有两套（`visible_documents_q` 和 `chroma_access_filter`）？

> 列表页走 MySQL 过滤；问答走向量库过滤。只做一套，另一条路径就会泄露数据。这是「权限必须覆盖所有数据出口」的典型体现。

**自测**：普通员工能不能搜到财务部的文档？→ 不能，除非该文档是 public。

### 3.3 读 `apps/documents/services/parser.py` 与 `chunking.py`

- `parser.py`：按扩展名分发，pdf 用 pypdf，docx 用 python-docx，txt/md 直接读
- `chunking.py`：`RecursiveCharacterTextSplitter`，按 `\n\n` → `\n` → `。` → … 逐级降级切分

**面试点**：为什么要 overlap（重叠）？→ 防止一句话被切在两块中间，导致检索时语义断裂。

**面试点**：chunk_size 怎么定？→ 太大检索不精准且费 token；太小上下文不全。本项目 800/120，可按文档类型调。

### 3.4 读 `apps/documents/services/vectorstore.py`

**讲解**：向量库封装，关键是**可替换**：

- `HashEmbeddingFunction`：本地哈希假向量，纯粹为了没模型时能联调
- `get_embedding_function`：真正生产用 sentence-transformers 或 API
- `get_chroma_client` / `get_collection`：连 Chroma
- `upsert_chunks` / `delete_document_vectors` / `search_similar`：增删查

**面试点**：为什么单独抽一层 service？→ 换 Milvus/pgvector 时只改这个文件，上层不动。

### 3.5 读 `apps/documents/tasks.py`（异步核心）

**讲解**：`process_document_task` 的完整流程：

```
读 Document → 若不是待处理状态则跳过
  → 状态改 processing
  → parser 抽文本 → chunking 分块
  → 删旧向量 + 删旧 chunk（幂等，支持重跑）
  → upsert 到 Chroma
  → 事务写 DocumentChunk + 状态 ready
失败 → 重试 3 次（间隔递增）→ 最终 failed + error_message + webhook 告警
```

**面试点**：为什么异步？→ PDF 解析 + embedding 可能几十秒，堵在 HTTP 里用户会超时，也占满 gunicorn worker。

**面试点**：怎么保证幂等？→ 处理前先删掉该文档的旧向量和旧 chunk，重跑不会重复。

**面试点**：`acks_late=True` + `reject_on_worker_lost` 什么意思？→ 任务执行完才 ack，worker 崩了任务会重新投递，不丢。

### 3.6 读 `apps/documents/views.py` + `urls.py`

重点看 `DocumentListCreateView.post`：上传 → 判断角色决定初始状态 → 只有 total 能立即触发 Celery → 写审计。

审批接口 `DocumentApproveView`：校验总数权限 → 状态改 `pending` → `.delay()` 触发处理。

### 3.7 读 `apps/documents/management/commands/reindex_documents.py`

命令行工具：`python manage.py reindex_documents`。换 embedding 模型后重跑全部文档。

**阶段 3 过关标志**：能从「点上传按钮」讲到「Chroma 里出现向量」，中间每一步在哪个文件。

## 阶段 4：RAG 问答（3 小时，最有技术含量）

### 4.1 读 `apps/qa/models.py`

`QuestionSession`（一次会话）+ `QAMessage`（消息，assistant 带 sources）。会话按 `updated_at` 倒序。

### 4.2 读 `apps/qa/views.py`

- `AskView.post`：解析参数 → `_resolve_session` → 走 `stream` 与否 → `run_qa` → `_persist_qa` 落库 → `write_audit`
- `_stream_response`：SSE 格式 `event: xxx\ndata: json\n\n`，Nginx 需要 `proxy_buffering off`
- `SessionListView` / `SessionDetailView`：会话列表/详情/删除，都限 `user=request.user`；删除整个会话会级联删掉它的全部消息，先取标题和消息数快照再删，然后写 `session_delete` 审计
- `SessionMemoryView`：查看/清空会话记忆（清空会写审计日志），同样限 `user=request.user`

**前端位置**：会话列表每行一个「删除」按钮（`templates/qa.html` 的 `deleteSession`），侧栏底部还有「删除当前会话」按钮；删除请求期间会禁用所有删除入口并显示「删除中…」，防止重复点击删多了。

**易错点**：删除会话和清空记忆是两件事——`DELETE /api/qa/sessions/<id>/memory/` 只清摘要和上下文记忆、消息保留；`DELETE /api/qa/sessions/<id>/` 连会话带消息一起删，不可恢复。

**自测**：为什么 `SessionDetailView` 查询要带 `user=request.user`？→ 横向越权防护，A 用户不能看 B 用户的会话。

### 4.3 读 `apps/qa/graph.py`（重点中的重点）

按顺序读函数：

| 函数 | 干什么 |
|------|--------|
| `get_chat_llm` | 建 DeepSeek 客户端；没配 key 返回 None（降级） |
| `_parse_json_object` | 让 LLM 输出 JSON 时容错解析（直接 parse 失败就正则抠 `{...}`） |
| `build_context` | 把命中的 chunk 拼成带编号的上下文 `[1] 来源《…》` |
| `_access_where` | 生成检索权限条件，和 `chroma_access_filter` 保持一致 |
| `rewrite_node` | 查询改写，提升召回 |
| `retrieve_node` | 检索 Chroma |
| `grade_node` | 判断「检索到的内容够不够回答」，输出 `sufficient`/`insufficient` |
| `route_after_grade` | 条件边：不够且没超次数 → `expand_retrieve`；否则 → `generate` |
| `expand_retrieve_node` | 换策略扩大检索 |
| `generate_node` | 组装 prompt → 调 LLM → 返回答案 + sources |
| `build_qa_graph` / `get_qa_graph` | 组装并缓存状态图 |
| `run_qa` | 对外入口：把 user/问题转成 state，跑图，返回 dict |

`QAState` 是 TypedDict，图里所有节点共享这份状态。

**面试必答**：
1. **什么是 RAG？** 先检索、再生成，让 LLM 基于企业私有资料回答，减少幻觉、可溯源。
2. **为什么用 LangGraph 不用一条链？** 需要条件分支和循环（不够就再检索），还要可解释的 steps。
3. **怎么降低幻觉？** 上下文约束 prompt + grade 判断 + 返回 sources + 权限外资料根本检索不到。
4. **检索效果差怎么办？** 查询改写、调 top_k、换 embedding、调 chunk、二次扩检，看 steps 定位。

### 4.4 读 `apps/qa/memory.py` 与 `apps/qa/tasks.py`（多轮对话记忆）

**讲解**：这是让问答「记得住上下文」的地方，核心是三层：

| 层 | 载体 | 一句话 |
|----|------|--------|
| 短期记忆 | 最近 `MEMORY_WINDOW_TURNS` 轮（默认 6）原文 | 追问、省略、指代能接上 |
| 长期记忆 | `QuestionSession.summary` | 滑出窗口的旧对话压成摘要，关键信息不丢 |
| 上下文预算 | `MEMORY_MAX_HISTORY_CHARS`（默认 4000 字） | 从最新往前填，防止历史挤掉本轮检索资料 |

`memory.py` 里两个关键函数：

- `build_memory(session)`：组装 `MemorySnapshot`（历史消息 + 摘要 + 用量统计），供 graph 注入
- `update_rolling_summary(session)`：把滑出窗口的消息并入摘要；靠 `summarized_message_count` 保证幂等，不重复算

`tasks.py` 里的 `refresh_session_summary` 是 Celery 任务，**在回答落库之后异步更新摘要**，失败只记日志，不影响问答。

**三个最容易答错的点**：

1. **为什么必须在写入本轮消息之前构建记忆？** 否则历史里会混进当前这个问题，模型看到「自己刚问过一遍」，效果悄悄变差、而且不报错。
2. **为什么不把历史全塞进 prompt？** 历史太长会挤掉本轮检索到的资料，RAG 就失去了「依据资料回答」的根基。
3. **没有 API Key 怎么办？** 摘要退化成启发式拼接，改写节点退化成「拼接上一轮问题」，链路照样跑通。

**面试点**：记忆用量是**可见**的（响应的 `memory` 字段 + 前端提示），并且可以用 `use_memory: false` 单次关闭——可观测、可对照，才便于排查。

### 4.5 读 `apps/qa/services.py`、`serializers.py`、`urls.py`、`tests.py`

`services.py` 只是转发（`from qa.graph import run_qa`），这是「对外接口稳定、内部实现可换」的写法。

**阶段 4 过关标志**：能不看代码画出 LangGraph 的节点和边，说清 grade 之后的两种走向，并讲清多轮记忆的三层结构。

## 阶段 5：运维与安全横切（1.5 小时）

### 5.1 读 `apps/common/models.py` 与 `audit.py`

- `AuditLog`：action 枚举（login/upload/approve/ask/memory_reset/session_delete/staff_update…）+ 对象 + IP + 路径 + 成功与否 + detail JSON。新增枚举值要 `makemigrations`（见 `common/migrations/0003_alter_auditlog_action.py`）
- `write_audit(...)`：**所有异常都被吞掉只打日志**，保证审计失败不影响主流程

**面试点**：为什么把 action 做成枚举？→ 查询/统计方便，避免字符串拼错。

**面试点**：为什么审计写入要 try/except？→ 审计是旁路，不能因为它挂了导致用户登录失败。

### 5.2 读 `apps/common/views.py`

- `HealthView`：存活探针，返回 status/service/time/debug
- `ReadyView`：就绪探针，实测 DB（`ensure_connection`）和缓存（set/get），任一挂就 503
- `AuditLogListView`：只有总管理员能查，支持按 action 过滤 + 分页

**面试点**：存活和就绪有什么区别？→ 存活挂了要重启容器；就绪挂了只是暂时不接流量（比如 DB 还没起来）。

### 5.3 读限流相关

在 `config/settings.py` 的 `DEFAULT_THROTTLE_RATES` 和三个 view 里的 `ScopedRateThrottle`：

- `login` 20/min：防撞库
- `ask` 30/min：问答烧 LLM 的钱，必须限
- `upload` 20/min：防刷存储

注意 `DocumentListCreateView.get_throttles()` 里，GET 列表不限流，只有 POST 才限。

### 5.4 读 `templates/app_base.html`

**讲解**：所有页面的母版。核心是内联的 `KB` 对象：

- 存/取 token
- `KB.api(url, options)`：自动加 `Authorization` 头，401 时跳登录
- 启动时拉 `/api/auth/me/`，按 `is_super_admin` / `can_upload` 等字段决定导航显示

**面试点**：为什么后端要在 me 接口返回 `can_upload` 这类布尔字段？→ 前端据此渲染，避免前端硬编码角色判断逻辑、两边规则不一致。

## 阶段 6：部署与交付（1 小时）

### 6.1 读 `Dockerfile` + `docker-compose.yml`

五个服务：`db`(MySQL) / `redis` / `web`(gunicorn) / `worker`(celery) / `nginx`。

注意 compose 里显式覆盖了 `DEBUG=False`、`CELERY_TASK_ALWAYS_EAGER=False`、`USE_SQLITE=False` —— **生产环境不允许开发配置漏进去**。

web 的 command 是面试点：`migrate → collectstatic → gunicorn`，容器起来自动完成部署步骤。

### 6.2 读 `deploy/nginx.conf`

- 静态和 media 由 Nginx 直接返回（不进 Django）
- `/api/` 反代到 web，`proxy_buffering off` 是 SSE 流式必须的
- 底部注释块是 HTTPS 配置样例

### 6.3 读 `scripts/backup.sh` / `restore.sh` / `backup.ps1`

备份三样：MySQL dump、`media/`、`data/chroma/`。**向量库也要备份**，否则恢复后检索不到东西——这是很多人会漏的点。

### 6.4 读 `.env.example` 的生产检查清单

能背出五条：`DEBUG=False`、强 SECRET_KEY、真实 ALLOWED_HOSTS、强数据库密码、HTTPS + 安全 Cookie。

### 项目一句话
Django + DRF + JWT 做企业知识库，Celery 异步入库，Chroma 存向量，LangGraph 做多步 RAG 接 DeepSeek，带多角色权限、多轮会话记忆、限流、审计和 Docker 部署。

### 可以主动说的不足（加分）

- 记忆只到会话级，没有跨会话的用户级记忆；摘要有损，细节会丢
