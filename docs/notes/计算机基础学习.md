# 第一部分：数据结构与算法

## 1.0 复杂度分析：唯一能跨机器对话的语言

**解决什么问题**：你换台电脑、换个语言，跑出来的时间完全不同。需要一个与硬件无关的尺子，来比较两种做法的优劣。

**追问链**：

- *为什么不能直接跑一遍测时间？* 因为测出来的是"这台机器 + 这个语言 + 这份数据"的结果，换个环境就变了，而且 n 小的时候噪声占主导。
- *那 O(n) 到底在数什么？* 数的是"基本操作次数随 n 增长的**阶**"，把常数和低阶项都扔掉了。
- *凭什么能扔掉常数？* 因为当 n 足够大时，n 的增长会淹没任何常数。但**反过来要警惕**：n 小于某个规模时，常数是决定性的。这就是为什么小数组用插入排序反而比快排快——Timsort 就是靠这个，短段用插入排序。
- *同样是 O(n log n)，为什么快排比归并快？* 因为常数不同：快排原地做、访问连续内存；归并要额外开数组、频繁拷贝。渐进复杂度相同 ≠ 实际速度相同。
- *那"摊还 O(1)"又是什么？* 单次操作可能很贵，但把总代价摊到每次操作上是常数。动态数组扩容那次拷贝是 O(n)，但每 n 次 append 才发生一次，摊还下来是 O(1)。
- *最坏、平均、摊还，什么时候用哪个？* 实时系统（交易、控制）看**最坏**；通用场景看**平均**；数据结构自己的承诺用**摊还**。快排平均 O(n log n) 但最坏 O(n²)，所以它在实时系统里要换成归并或堆排。
- *那哈希表平均 O(1)、最坏 O(n)，为什么还敢用？* 因为好哈希函数下的最坏情况是极小概率事件。但如果是"攻击者能控制 key"，那就不是概率问题了——见 1.4 的 HashDoS。

**验证实验**：观察 list 扩容，算摊还成本。

```python
import sys

lst = []
prev = sys.getsizeof(lst)
for i in range(1, 2000):
    lst.append(i)
    size = sys.getsizeof(lst)
    if size != prev:
        print(f'len={len(lst):>5}  容量变化 {prev} -> {size}')
        prev = size
```

你会看到容量不是一个个涨，而是 0→4→8→16→24→32→40→…（CPython 用约 1.125 倍增长加偏移）。每次扩容拷贝的成本被摊到大量 append 上，所以 `append` 是摊还 O(1)。对比 `insert(0, i)`：

```python
import timeit

print('append   ', timeit.timeit('lst.append(1)', setup='lst=[]', number=100000))
print('insert(0)', timeit.timeit('lst.insert(0,1)', setup='lst=[]', number=100000))
```

`insert(0)` 每次都搬移全部元素，是 O(n)，差距会是几百倍。

**项目落点**：分页查询 `qs[start:start+page_size]` 是切片，不是逐条搬移；但如果写成"先取全量再切"，就把 O(1) 的切片变成了 O(n) 的全表加载。

## 1.1 数组：为什么随机访问是 O(1)

**解决什么问题**：需要按下标瞬间拿到第 i 个元素，不想从头找。

**追问链**：

- *为什么是 O(1)？* 地址 = 首地址 + i × 元素大小。这是纯乘法，一步到位。
- *这条公式依赖什么前提？* 依赖**每个元素等长**。变长元素就没法直接算地址——这也是为什么 Python 的 list 存的其实是指针（定长 8 字节），不是对象本体。
- *那插入删除为什么是 O(n)？* 中间插一个，后面的元素必须整体后移，腾出位置。
- *"数组遍历比链表快"的真正原因是什么？* 不是复杂度，是**空间局部性**。数组元素在内存里连续，CPU 读到第 1 个元素时，整个缓存行（64 字节）都被载入，后面十几个元素直接从缓存拿。链表节点散落在堆的各个角落，每次跳指针都可能是一次缓存未命中。
- *既然连续这么好，为什么动态数组扩容要按倍数扩？* 因为要摊还。如果每次只多扩一个位置，那每次 append 都要拷贝，总代价 O(n²)。按 2 倍扩，总拷贝次数约 2n，摊还 O(1)。
- *为什么很多实现用 1.5 倍而不是 2 倍？* 2 倍增长永远无法复用之前释放的内存块（每次都要求更大的连续空间），1.5 倍在若干次之后旧块总和大到能容纳新块，可以复用、减少碎片。代价是摊还常数略差。

**代价与取舍**：数组用"插入删除慢"换来了"随机访问快 + 缓存友好"。绝大多数场景值得。

**验证实验**：局部性的可观测证据。

```python
import numpy as np
import time

n = 3000
a = np.zeros((n, n), dtype=np.float64)

t = time.perf_counter()
for i in range(n):
    a[i, :] += 1.0          # 行优先：连续内存
row_time = time.perf_counter() - t

t = time.perf_counter()
for i in range(n):
    a[:, i] += 1.0          # 列优先：每次跨一整行
col_time = time.perf_counter() - t

print(f'行优先 {row_time:.3f}s   列优先 {col_time:.3f}s   慢 {col_time/row_time:.1f} 倍')
```

同一块内存、同样 900 万次加法，列优先会慢几倍到十几倍。**这就是缓存行的力量**——没写过这段代码，你对"局部性"只有抽象印象。

**项目落点**：向量检索里，同一个文档的分块在 Chroma 里是连续存储的，按 `document_id` 顺序读取比随机跨文档读要快得多。

## 1.2 链表：用访问速度换增删速度

**解决什么问题**：频繁在中间插入删除，又不想每次搬移整个数组。

**追问链**：

- *插入为什么是 O(1)？* 改两个指针就行。但注意：**前提是你已经拿到了那个位置**。按值查找仍然是 O(n)。
- *那链表的"O(1) 插入"有什么陷阱？* 单链表中要删除某个节点，你必须先找到它的前驱，所以实际是 O(n)。这就是**双向链表存在的第一个理由**。
- *双向链表又多花一个指针，值吗？* 在 LRU 缓存里值——需要在 O(1) 时间内把任意节点摘下来再挂到头部，没有前驱指针做不到。
- *链表为什么比数组慢那么多？* 三个叠加：① 随机分布导致缓存不友好；② 每个节点多一个指针的内存开销；③ CPU 预取器无法预测下一个地址。
- *那链表在真实系统里还有什么用？* 内核的 task 队列、Redis 的 list、哈希表的拉链（1.4 会讲）。

**验证实验**：头插的代价对比。

```python
import timeit

print('list.insert(0)  ', timeit.timeit('lst.insert(0,1)', setup='lst=list(range(10000))', number=10000))
print('deque.appendleft', timeit.timeit('dq.appendleft(1)', setup='from collections import deque; dq=deque(range(10000))', number=10000))
```

`list` 每次头插搬移一万个指针，`deque` 是双向链表分块实现，头尾都是 O(1)。差距是数量级的。

## 1.3 栈与队列：顺序本身是一种信息

**解决什么问题**：很多问题的答案取决于"处理顺序"。后进先出还是先进先出，决定了算法的形态。

**追问链**：

- *栈为什么能解决函数调用？* 因为函数的生命周期天然嵌套：A 调用 B，B 必须比 A 先结束。后进先出正好匹配这种嵌套结构。函数调用栈、表达式求值、括号匹配、DFS 都是这个形状。
- *队列为什么能解决最短路径？* 因为 BFS 逐层扩展，先进先出保证"距离近的先被处理"，所以第一次到达目标就是最短。
- *用数组实现队列有什么问题？* 出队要搬移（O(n)），或者用两个下标做循环队列。
- *优先队列和普通队列有什么区别？* 不出队首，出"优先级最高的"。用堆实现，插入和取出都是 O(log n)。操作系统调度、任务队列、定时器都是它。

**验证实验**：两个栈实现队列。

```python
class QueueWithTwoStacks:
    def __init__(self):
        self.inn, self.out = [], []

    def push(self, x):
        self.inn.append(x)

    def pop(self):
        if not self.out:
            while self.inn:
                self.out.append(self.inn.pop())
        return self.out.pop()

q = QueueWithTwoStacks()
for i in range(5):
    q.push(i)
print([q.pop() for _ in range(5)])   # [0, 1, 2, 3, 4]
```

每个元素最多被搬运两次，所以摊还 O(1)。**这个"搬运两次"的账要和 1.0 的摊还分析对上**。

**项目落点**：Celery 的 broker 就是队列；Redis 的 `list` 类型做队列（LPUSH/BRPOP）；你的任务优先级如果想做，就得换成有序集合或堆。

## 1.4 哈希表：把"查找"变成"计算"

**解决什么问题**：数组靠下标 O(1) 访问，但现实里的 key 是字符串、是 ID、是元组。需要一种方法把任意 key 直接算成下标。

**追问链**：

- *哈希函数做什么？* 把任意长度的输入映射成固定范围的整数。好的哈希函数要满足：计算快、分布均匀、雪崩效应（输入变一位，输出大不同）。
- *为什么还要取模？* 哈希值可能很大（Python 的 hash 是 64 位），要压到桶的数量范围内。
- *桶数量为什么常取质数或 2 的幂？* 取质数是为了避免与哈希值有公因子导致分布不均（经典做法 `h % prime`）。取 2 的幂是为了用位运算 `h & (n - 1)` 替代取模，快得多——Java HashMap 和 CPython 都这么做，代价是哈希函数必须把低位也打散。
- *不同 key 算出同一个下标怎么办（冲突）？* 两大路线：**链地址法**（每个桶挂一个链表）和**开放寻址法**（冲突了就按探测序列找下一个空槽）。
- *两者的取舍是什么？* 拉链法：负载因子可以超过 1，删除干净利落，但要额外指针、内存不连续。开放寻址：全部数据在一个数组里、缓存友好，但负载因子必须小于 1，删除需要墓碑标记，而且容易"聚集"（连续占用导致探测链变长）。**CPython 的 dict 用的是开放寻址，Java HashMap 用的是拉链（链表超过 8 个转红黑树）**。
- *负载因子是什么，为什么通常 0.66~0.75？* 已用桶 / 总桶数。太低浪费空间，太高冲突剧增。Java HashMap 默认 0.75，CPython dict 在 2/3 时扩容。这个数字不是拍的，是在空间和冲突率之间测出来的折中。
- *为什么 Python 3.6 之后 dict 变成有序的？* 因为改成了"紧凑布局"：一个稀疏的索引数组 + 一个紧凑的条目数组，条目按插入顺序排列。遍历就是顺序遍历条目数组，顺便还省了内存（这是 3.7 升格为语言保证的实现基础）。
- *哈希表最坏情况能坏到什么程度？* O(n)——所有 key 撞到一个桶。如果是攻击者能控制输入，他可以专门构造这种 key，让服务器 CPU 打满，这叫 **HashDoS**。
- *怎么防 HashDoS？* 给哈希函数加随机种子（进程启动时随机），攻击者无法离线预测。CPython 默认开启 `PYTHONHASHSEED` 随机化，用的就是 SipHash。

**代价与取舍**：哈希表用"无序"换来了 O(1) 查找。所以它做不了范围查询（`BETWEEN`、`ORDER BY`）——这一点在 1.6 讲数据库索引时会成为关键。

**验证实验一**：自己写一个拉链哈希表，观察负载因子和平均链长的关系。

```python
class ChainedHashMap:
    def __init__(self, buckets=8):
        self.buckets = buckets
        self.table = [[] for _ in range(buckets)]
        self.size = 0

    def _index(self, key):
        return hash(key) % self.buckets

    def put(self, key, value):
        bucket = self.table[self._index(key)]
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket[i] = (key, value)
                return
        bucket.append((key, value))
        self.size += 1

    def get(self, key):
        for k, v in self.table[self._index(key)]:
            if k == key:
                return v
        raise KeyError(key)

    def stats(self):
        lengths = [len(b) for b in self.table]
        load = self.size / self.buckets
        return load, max(lengths), sum(lengths) / self.buckets

m = ChainedHashMap(buckets=8)
for i in range(100):
    m.put(i, i * 2)
load, longest, avg = m.stats()
print(f'负载因子 {load:.2f}  最长链 {longest}  平均链长 {avg:.2f}')
```

固定 8 个桶塞 100 个元素，负载因子 12.5，最长链会非常难看——这就是必须扩容的原因。把 `buckets` 调到 256 再看一次。

**验证实验二**：制造冲突，看退化。

```python
# 故意让所有 key 落在同一个桶
class BadHash(str):
    def __hash__(self):
        return 42

import timeit
good = {str(i): i for i in range(10000)}
bad = {BadHash(str(i)): i for i in range(10000)}

t1 = timeit.timeit(lambda: bad[BadHash('9999')], number=100000)
t2 = timeit.timeit(lambda: good['9999'], number=100000)
print(f'全部冲突 {t1:.4f}s   正常 {t2:.4f}s   退化 {t1/t2:.0f} 倍')
```

CPython 对这种情况有保护（当探测链过长会转成"分裂表"），但退化依然肉眼可见。

**项目落点**：`Document.content_hash` 加 `db_index=True`，本质就是让数据库在哈希值上建索引，把全表扫描变成近似一次查找。另外注意 Python 的 `hash()` 只保证进程内一致，**不要把它当成持久化指纹**（这就是为什么秒传必须用 SHA-256 而不是 `hash()`）。

## 1.5 树：有序 + 快速查找，怎么兼得

**解决什么问题**：哈希表 O(1) 但不支持范围查询和排序。数组有序但插入慢。树想要两者兼得。

**追问链**：

- *二叉搜索树靠什么保证查找快？* 左子树全比根小、右子树全比根大，每比较一次排除一半，O(log n)——**前提是树是平衡的**。
- *不平衡会怎样？* 如果按有序序列插入，树退化成一条链，查找变回 O(n)。
- *怎么保证平衡？* 红黑树、AVL 树通过旋转调整。
- *红黑树和 AVL 怎么选？* AVL 平衡更严格（左右子树高度差 ≤ 1），查找更快，但插入删除引发的旋转更多。红黑树放松了平衡（最长路径不超过最短路径的两倍），插入删除更省事。所以**查找密集用 AVL，增删频繁用红黑树**——STL 的 `map`、Java 的 `TreeMap`、Linux 内核的 CFS 调度器都用红黑树。
- *那数据库索引为什么不用红黑树？* 关键转折点：**红黑树是二叉的，高度约 log₂(N)**。2000 万行数据，高度约 25 层。如果每层都是一次磁盘 IO，就是 25 次 IO。要减少 IO，唯一的办法是**降低树高**，而降低树高的办法是**提高每个节点的扇出**——从"两个分叉"变成"一千个分叉"，这就走向了多叉树，也就是 B 树。详见 1.6。

**树家族速查**（每个都要能说出"为什么存在"）：

- 二叉搜索树：有序查找的起点，但不平衡
- 红黑树 / AVL：自平衡的二叉搜索树
- B 树 / B+ 树：为磁盘设计的多叉树
- 堆：只关心最值，不关心全局有序（见 1.7）
- Trie：按字符分叉，解决前缀匹配（路由表、自动补全、搜索联想）
- 线段树 / 树状数组：区间查询和区间更新（统计、排行榜）

**验证实验**：BST 退化。

```python
import sys
sys.setrecursionlimit(100000)

class Node:
    __slots__ = ('val', 'left', 'right')
    def __init__(self, val):
        self.val, self.left, self.right = val, None, None

def insert(root, val):
    if root is None:
        return Node(val)
    cur = root
    while True:
        if val < cur.val:
            if cur.left is None:
                cur.left = Node(val); return root
            cur = cur.left
        else:
            if cur.right is None:
                cur.right = Node(val); return root
            cur = cur.right

def depth(root):
    return 0 if root is None else 1 + max(depth(root.left), depth(root.right))

import random
ordered = None
for i in range(2000):
    ordered = insert(ordered, i)

shuffled = None
nums = list(range(2000)); random.shuffle(nums)
for i in nums:
    shuffled = insert(shuffled, i)

print(f'有序插入深度 {depth(ordered)}')     # 2000，退化成链
print(f'随机插入深度 {depth(shuffled)}')    # 约 20，log2(2000) ≈ 11
```

2000 个元素，有序插入深度 2000，随机插入深度约 20。**这就是"平衡"两个字的实际重量。**

## 1.6 B 树与 B+ 树：为磁盘而生的数据结构

**解决什么问题**：数据大到内存装不下，必须存在磁盘上。磁盘的访问代价是内存的十万倍，所以"访问次数"成了唯一重要的指标，而"比较次数"不再重要。需要一种把磁盘访问次数压到最低的树。

**完整追问链**（这段是面试官最爱一路问到底的题）：

- *为什么"磁盘 IO 少"值得专门优化？* 因为差距是量级级别的。内存随机访问约 100 纳秒，SSD 随机读约 100 微秒，机械硬盘寻道约 10 毫秒。差了十万倍。把页读取次数从 25 次降到 3 次，性能直接赢一个数量级。
- *一次"访问"的粒度是多少？* InnoDB 按**页**读，一页 16KB。所以"IO 次数"就是"读了多少页"。
- *那为什么不用二叉搜索树或红黑树？* 高度 log₂(N)。2000 万行约 25 层，每层一次页读，25 次。
- *换成多叉树，一个节点能放多少 key？* 一个 16KB 页，去掉页头页尾约 15KB 可用。假设 key 是 bigint（8 字节），页内指针 6 字节，一条索引项约 14 字节，能放 **1000 多个**，也就是大约 1000 路。
- *那高度是多少？* log₁₀₀₀(2×10⁷) ≈ 3。三次页读。而且根节点几乎总在内存里，实际只要 2 次。**这才是"树矮"的真实含义**——矮不是形容词，是一个算出来的数字。
- *为什么不用哈希索引？* 哈希把 key 打散，有序性彻底没了。`BETWEEN`、`ORDER BY`、`>`、`<`、前缀匹配全都做不了。索引的职责不只是"查找"，还要"排序"和"扫一段"。
- *那为什么 B 树不行，非要 B+ 树？* 两点：① **B 树的非叶子节点也存真实数据行**，同样一页能装的 key 就少得多，扇出变小、树变高；B+ 树非叶子只存 key，扇出最大化。② **B+ 树的叶子节点用链表串起来**，范围扫描顺着叶子链表走一遍就行；B 树需要在树里来回跳。
- *16KB 这个数字怎么来的？* 权衡出来的。页越大 → 树越矮，但单次读的浪费越多、内存里能缓存的页越少。页越小 → 扇出小、树高。InnoDB 默认 16KB，是历史上针对机械盘定下的值，SSD 时代其实偏保守，但改它要整体评估。
- *"最左前缀"为什么成立？* 因为 B+ 树里的 key 是按联合索引的**列顺序**排序的。树只能在"有序的前缀"上做定位。跳过第一列，剩下的列在整棵树里根本就不是有序的，无法二分。
- *索引为什么会失效？* 每一类失效都对应一个"破坏了有序性"的动作：在列上做函数运算（值变了）、隐式类型转换（值变了）、前导模糊 `LIKE '%x'`（前缀不定，无法定位）、范围条件之后的列（后续列不再有序）、`OR` 连接不同列。
- *那"回表"是什么？* 二级索引的叶子存的是主键值，不是整行。查到主键后还要再去主键索引（聚簇索引）里取整行，这次额外查找就叫回表。
- *怎么避免回表？* 覆盖索引——把查询要用的列都放进索引，这样二级索引的叶子就能直接给出答案，不用回表。

**验证实验**：用 SQLite 实测索引的威力。

```python
import sqlite3, time, random

conn = sqlite3.connect(':memory:')
cur = conn.cursor()
cur.execute('CREATE TABLE docs (id INTEGER PRIMARY KEY, title TEXT, content_hash TEXT, status TEXT)')

rows = [(i, f'文档{i}', f'{random.getrandbits(128):032x}', random.choice(['ready','pending'])) for i in range(1, 200001)]
cur.executemany('INSERT INTO docs VALUES (?,?,?,?)', rows)
conn.commit()

target = 'ready'
cur.execute('EXPLAIN QUERY PLAN SELECT count(*) FROM docs WHERE status = ?', (target,))
print('建索引前:', cur.fetchall())

t = time.perf_counter()
cur.execute('SELECT count(*) FROM docs WHERE status = ?', (target,)).fetchone()
print(f'建索引前耗时 {time.perf_counter()-t:.4f}s')

cur.execute('CREATE INDEX idx_status ON docs(status)')
conn.commit()

cur.execute('EXPLAIN QUERY PLAN SELECT count(*) FROM docs WHERE status = ?', (target,))
print('建索引后:', cur.fetchall())

t = time.perf_counter()
cur.execute('SELECT count(*) FROM docs WHERE status = ?', (target,)).fetchone()
print(f'建索引后耗时 {time.perf_counter()-t:.4f}s')
```

`EXPLAIN QUERY PLAN` 从 `SCAN docs` 变成 `SEARCH docs USING INDEX idx_status`，耗时差距是几十倍。**亲眼看到 `SCAN` 变 `SEARCH` 的那一刻，索引才从概念变成工具。**

再补一段验证"最左前缀"：

```python
cur.execute('CREATE INDEX idx_ab ON docs(status, title)')
conn.commit()

for sql in [
    'SELECT count(*) FROM docs WHERE status = ?',              # 能走索引
    'SELECT count(*) FROM docs WHERE status = ? AND title = ?', # 能走索引
    'SELECT count(*) FROM docs WHERE title = ?',               # 用不上
]:
    cur.execute('EXPLAIN QUERY PLAN ' + sql, ('ready',) if sql.count('?') == 1 else ('ready', '文档1'))
    print(sql[:52], '->', cur.fetchall()[0][-1])
```

第三条会显示全表扫描，因为跳过了最左列。

**项目落点**：`Document.status` 已经有 `db_index=True`；秒传要加 `content_hash` 索引；文档列表用 `select_related('department', 'uploader', 'reviewed_by')` 正是为了避免每条记录回表式地额外查库（N+1）。

## 1.7 堆：只关心最值，不关心全局有序

**解决什么问题**：数据是动态的，反复要问"当前最大/最小的是哪个"。每问一次就排一次序，是 O(n log n)，太贵。

**追问链**：

- *堆和排序的区别？* 排序给出**全序**，任意两个元素都能比大小；堆只保证**堆顶是最值**。取最值 O(1)，插入和删除 O(log n)。
- *堆用什么物理结构存？* 完全二叉树，但**用数组存、不用指针**。父节点下标 i，左子 2i+1，右子 2i+2，父 (i-1)//2。用数组是为了缓存友好——真的用指针连二叉树，每次上下走都是随机内存访问（回想 1.1 的列优先实验）。
- *插入和删除怎么维持性质？* 插入放末尾然后"上浮"；删除堆顶时把末尾元素搬到根再"下沉"。都是 O(log n)，因为树高就是 log n。
- *建堆为什么是 O(n)，不是 O(n log n)？* 直觉是"n 个元素各下沉一次，每次 O(log n)"，但这是粗糙的上界。真相是**大部分节点在树的底层，而底层节点能下沉的深度很小**。求和 ∑(该层节点数 × 该层高度) 收敛到约 2n，所以是线性的。
- *为什么 Python 的 `heapq` 是最小堆？* 最小堆更常用（定时器、合并有序流、Dijkstra）。要最大堆就把值取负。
- *Top K 为什么用堆不用排序？* 复杂度从 O(n log n) 降到 O(n log k)。k 远小于 n 时差距巨大：一亿条数据取前 10，排序要比较约 27 亿次，堆只要约 3 亿次。

**代价与取舍**：堆放弃了"快速查找任意元素"——在堆里找一个指定的值是 O(n)。它只承诺最值这一件事。

**验证实验**：Top K 两种做法对比。

```python
import heapq
import random
import time

data = [random.randint(0, 10**7) for _ in range(2_000_000)]

t = time.perf_counter()
top_sort = sorted(data, reverse=True)[:10]
t_sort = time.perf_counter() - t

t = time.perf_counter()
top_heap = heapq.nlargest(10, data)
t_heap = time.perf_counter() - t

print(f'排序取前 10  {t_sort:.4f}s')
print(f'堆取前 10    {t_heap:.4f}s   快 {t_sort / t_heap:.1f} 倍')
print('结果一致:', top_sort == top_heap)
```

再验证"建堆是线性的"——把耗时除以规模，看这个比值稳不稳定：

```python
import heapq
import random
import time

for n in [100_000, 200_000, 400_000, 800_000]:
    data = [random.random() for _ in range(n)]
    t = time.perf_counter()
    heapq.heapify(data)
    elapsed = time.perf_counter() - t
    print(f'n={n:>8}  {elapsed * 1000:>7.2f}ms   耗时/规模 {elapsed / n * 1e6:.4f}us')
```

如果"耗时/规模"这一列基本恒定，说明是线性；如果随 n 一起涨，说明带 log。**自己量一次，比背一句"O(n)"扎实得多。**

**项目落点**：Celery 要支持任务优先级，底层就是优先队列；文档处理任务的失败重试若要做退避调度，定时器也是最小堆（Redis 的 zset 用跳表，见 1.11）。

## 1.8 图：关系本身也是数据

**解决什么问题**：很多对象的结构不是"一条列表"，而是"一张网"——谁依赖谁、哪条路最近、谁和谁连通。用数组和字典表达不了"关系"，需要专门的模型。

**追问链**：

- *邻接表和邻接矩阵怎么选？* 稀疏图（边数远小于 n²）用邻接表，省空间、遍历邻居快；稠密图用矩阵，判断两点是否相邻是 O(1)。社交网络是稀疏的，用表；小规模全连接用矩阵。
- *BFS 和 DFS 分别解决什么？* BFS 逐层扩展，能求出**无权图的最短路径**；DFS 一条路走到底，适合**连通性判断、拓扑排序、环检测**。
- *BFS 为什么能给出最短路径？* 队列保证"先入队的先处理"，也就是按层推进。第一次到达终点，必然是边数最少的走法。换成栈（DFS）就没这个性质。
- *拓扑排序解决什么问题？* 依赖顺序——编译顺序、任务调度、包安装。Kahn 算法不断取出入度为 0 的节点；如果最后没能输出全部节点，说明**存在环**，这本身就是环检测。
- *最短路径三种算法怎么选？* Dijkstra：非负权，堆优化后 O((V+E) log V)。Bellman-Ford：能处理负权、能检测负环，O(VE)。Floyd：全源最短路径，O(V³)，适合小图。
- *为什么 Dijkstra 不能有负权边？* 它基于贪心——"一旦某个点被确定，它的距离就不会再变小"。负权边会打破这个前提，导致已确定的结论失效。

**验证实验**：拓扑排序 + 环检测。

```python
from collections import deque

def topo_sort(graph):
    indeg = {node: 0 for node in graph}
    for node in graph:
        for nxt in graph[node]:
            indeg[nxt] += 1

    queue = deque([n for n, d in indeg.items() if d == 0])
    order = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for nxt in graph[node]:
            indeg[nxt] -= 1
            if indeg[nxt] == 0:
                queue.append(nxt)
    return order if len(order) == len(graph) else None   # None = 有环

deps = {
    'db': [],
    'models': ['db'],
    'permissions': ['models'],
    'serializers': ['models'],
    'views': ['serializers', 'permissions'],
    'urls': ['views'],
}
print('处理顺序:', topo_sort(deps))
print('有环示例:', topo_sort({'a': ['b'], 'b': ['c'], 'c': ['a']}))
```

把依赖换成你项目的模块图跑一遍，你会看到 Django 的 import 顺序其实就是一个拓扑排序的结果。

## 1.9 排序：为什么快排最快，为什么实际却用 Timsort

**解决什么问题**：把无序变有序，让后续的二分、归并、扫描都变便宜。

**追问链**：

- *比较排序为什么下界是 O(n log n)？* 决策树证明：n 个元素有 n! 种排列，每次比较最多把可能性分成两支，所以决策树高度至少 log₂(n!) ≈ n log n。这是**信息论意义上的下界**，任何基于比较的算法都突破不了。
- *那快排为什么平均最快？* 三个因素叠加：原地排序（不额外开空间）、顺序访问（缓存友好）、内层循环简单（常数小）。
- *快排最坏什么时候发生？* pivot 选得极端。比如对已排序数组取首元素做 pivot，每次只能分出一个元素，退化成 O(n²)。解决办法是随机选 pivot 或三数取中。
- *归并比快排慢在哪？* 要开额外数组、要来回拷贝。但它**稳定**，而且最坏也是 O(n log n)——所以实时系统和外部排序（文件大到内存装不下）用它。
- *堆排呢？* 空间 O(1)、最坏 O(n log n)，看起来完美，但父子节点下标相隔很远，访问跳跃、缓存极不友好，实测比快排慢。
- *"稳定"是什么意思，为什么要关心？* 排序后相等元素的相对顺序保持不变。多关键字排序时至关重要：先按状态排、再按时间排，如果第二次排序不稳定，第一次的结果就被打乱了。
- *Python 的 `sorted` 用的什么？* Timsort——归并 + 插入排序的混合体。核心洞察是**真实数据往往部分有序**：它先扫描出已有的有序段（run），再合并这些段。所以对几乎有序的数据，它接近 O(n)，而快排反而退化成 O(n²)。
- *计数排序、基数排序为什么能突破 n log n？* 它们不做比较，直接按值的范围定位。代价是只适用于值域有限的整数或定长字符串——**"突破下界"从来不是免费的，是换了一个前提。**

**验证实验**：快排的退化是能看见的。

```python
import random
import time

def quicksort(arr):
    if len(arr) <= 1:
        return arr
    pivot = arr[len(arr) // 2]
    left = [x for x in arr if x < pivot]
    mid = [x for x in arr if x == pivot]
    right = [x for x in arr if x > pivot]
    return quicksort(left) + mid + quicksort(right)

def quicksort_worst(arr):
    """故意取首元素做 pivot —— 对已排序数据会退化"""
    if len(arr) <= 1:
        return arr
    pivot = arr[0]
    left = [x for x in arr[1:] if x < pivot]
    right = [x for x in arr[1:] if x >= pivot]
    return quicksort_worst(left) + [pivot] + quicksort_worst(right)

n = 2000
random_data = [random.randint(0, 10**6) for _ in range(n)]
sorted_data = sorted(random_data)

t = time.perf_counter(); quicksort(random_data[:]); print(f'快排(随机数据)   {time.perf_counter()-t:.4f}s')
t = time.perf_counter(); quicksort(sorted_data[:]); print(f'快排(有序数据)   {time.perf_counter()-t:.4f}s')
t = time.perf_counter(); quicksort_worst(sorted_data[:]); print(f'首元素pivot(有序) {time.perf_counter()-t:.4f}s')
t = time.perf_counter(); sorted(random_data); print(f'内置 sorted      {time.perf_counter()-t:.4f}s')
```

最后两行的对比最值得看：**有序数据 + 首元素 pivot** 会慢出量级，而内置 `sorted` 面对有序数据反而更快——因为 Timsort 直接识别出了那个有序段。

## 1.10 算法设计思想：五种套路

**解决什么问题**：具体算法记不完，但"解题的思路"只有几种。面试考的是你能不能判断该用哪一种。

| 思想 | 什么时候能用 | 关键判据 | 典型例子 |
|---|---|---|---|
| 分治 | 问题能拆成同类子问题 | 子问题独立、结果能合并 | 归并、快排、二分查找 |
| 贪心 | 每步取局部最优能导向全局最优 | **必须能证明**，证不出来就别用 | 活动选择、Huffman 编码、最小生成树 |
| 动态规划 | 有重叠子问题 + 最优子结构 | 子问题会重复、当前决策依赖过去的解 | 背包、编辑距离、最长公共子序列 |
| 回溯 | 解空间是一棵树，需要试错 | 需要"尝试 + 撤销" | 全排列、N 皇后、数独 |
| 二分答案 | 答案落在一个单调的数值区间 | 能写出"给定值是否可行"的单调判定函数 | 最小化最大值、容量规划 |

**追问链**：

- *贪心和 DP 的分界线在哪？* 贪心做一次决策就不回头；DP 保留所有子问题的解。贪心快但容易错，DP 稳但费空间。分界的唯一依据是**证明**——能证明"局部最优可推出全局最优"才能用贪心，证不出来就用 DP。
- *为什么 DP 是"用空间换时间"？* 因为有重叠子问题会被反复求解。用一个表把算过的结果存下来，就只算一次。复杂度从指数级降到多项式级。
- *"二分答案"和"二分查找"什么关系？* 同一种思维：在单调区间上不断验证中点。查找是在有序数组上二分，答案二分是在数值范围上二分——**判定函数替代了数组下标**。
- *回溯为什么必须剪枝？* 不剪就是暴力枚举，指数级。剪枝的本质是"提前判断这条路不可能有解"，尽早砍掉子树。

**验证实验**：二分答案求"分割数组的最小最大和"。

```python
def can_split(nums, k, limit):
    """能否把 nums 分成不超过 k 段，且每段的和都不超过 limit"""
    count, current = 1, 0
    for num in nums:
        if num > limit:
            return False
        if current + num > limit:
            count += 1
            current = num
            if count > k:
                return False
        else:
            current += num
    return True

def split_array(nums, k):
    lo, hi = max(nums), sum(nums)
    while lo < hi:
        mid = (lo + hi) // 2
        if can_split(nums, k, mid):
            hi = mid        # 可行，试着更小
        else:
            lo = mid + 1    # 不可行，必须更大
    return lo

print(split_array([7, 2, 5, 10, 8], 2))   # 18
```

注意这里没有数组可以二分，二分的是**答案的取值范围** `[max(nums), sum(nums)]`。判定函数 `can_split` 是单调的——上限越大越容易分段成功，这正是能二分的前提。

## 1.11 进阶结构：面试高频的五个

### 跳表（Skip List）

**解决什么问题**：链表查找是 O(n)。想加速就得加索引，但维护一个多层索引、还要保证平衡，很麻烦。跳表用**随机层级**替代了平衡树复杂的旋转逻辑。

**追问链**：

- *跳表靠什么保证速度？* 每个节点随机决定自己"升几级"。期望上每上升一层节点数减半，所以查找是期望 O(log n)。
- *Redis 为什么用跳表不用红黑树？* 三个理由：① 实现简单得多，红黑树的旋转和变色逻辑很难写对；② **范围查询天然方便**——找到起点后顺着底层链表一路走就行，红黑树得反复做中序遍历；③ 并发环境下更容易改造成无锁结构。
- *代价是什么？* 多级索引占额外空间；最坏情况仍是 O(n)（虽然概率极低）。**它用"空间 + 随机性"换来了"实现简单"。**

### 布隆过滤器（Bloom Filter）

**解决什么问题**：判断"某个东西**一定不存在**"，而且要用极少的空间。典型场景是挡在数据库前面的第一道闸门。

**追问链**：

- *原理是什么？* 一个位数组 + k 个哈希函数。插入元素时把它的 k 个哈希位置置 1；查询时看这 k 位是不是全为 1。
- *为什么会有假阳性？* 不同元素可能把彼此的位置占了。一个从没插入过的元素，它的 k 位恰好被别人置成了 1，于是被误判为"存在"。
- *为什么不会有假阴性？* 元素一旦插入，它的 k 位必然被置 1，之后没人会清空它们。所以"查询说全 1"是必要条件但不充分。**这个不对称性正是它的价值**：说"不存在"绝对可信，说"存在"可能误报。
- *为什么这个不对称正好有用？* 因为缓存穿透要挡的就是"确定不存在"的请求。布隆过滤器说"不存在"就直接返回，绝不错杀；说"可能存在"就去查库，偶尔多查一次无所谓。
- *怎么调参？* 位数组越大、哈希函数越多个，误报率越低，但空间和计算增加。误报率约等于 (1 - e^(-kn/m))^k，其中 m 是位数、n 是元素数、k 是哈希个数。
- *真实系统里谁在用？* 缓存穿透防护、爬虫 URL 去重、LSM 树数据库判断"这个 key 肯定不在这个文件里"（HBase、RocksDB）。

**验证实验**：亲手测出"假阴性一定是 0"。

```python
import hashlib

class BloomFilter:
    def __init__(self, bits=1_000_000, k=7):
        self.bits = bits
        self.k = k
        self.data = bytearray(bits // 8 + 1)

    def _positions(self, item):
        digest = hashlib.sha256(item.encode()).digest()
        for i in range(self.k):
            yield int.from_bytes(digest[i * 4:i * 4 + 4], 'big') % self.bits

    def add(self, item):
        for p in self._positions(item):
            self.data[p >> 3] |= 1 << (p & 7)

    def __contains__(self, item):
        return all(self.data[p >> 3] & (1 << (p & 7)) for p in self._positions(item))

bf = BloomFilter(bits=100_000, k=7)
for i in range(10_000):
    bf.add(f'user:{i}')

missed = sum(1 for i in range(10_000) if f'user:{i}' not in bf)
false_positive = sum(1 for i in range(10_000, 30_000) if f'user:{i}' in bf)

print(f'假阴性（漏报）: {missed}')
print(f'假阳性（误报）: {false_positive} / 20000 = {false_positive / 20000:.2%}')
```

把 `bits` 改成 1_000_000 再跑一次，看误报率降到多少。**这个 0 不是运气，是结构决定的。**

### LRU 缓存

**解决什么问题**：缓存容量有限，满了必须淘汰。淘汰谁？"最近最少使用的"——背后是时间局部性假设：刚被用过的数据，接下来还会被用。

**追问链**：

- *为什么需要"哈希表 + 双向链表"两个结构配合？* 哈希表提供 O(1) 定位节点，双向链表提供 O(1) 摘除和插入。只用哈希表不知道"谁最久没用"；只用链表查找是 O(n)。
- *LRU 和 LFU 怎么选？* LRU 看"最近用没用"，LFU 看"总共用了多少次"。LRU 有个著名弱点：一次全表扫描会把整个缓存冲空（所有老数据都被"访问"了一遍），这时要用 LFU 或 LRU-K。
- *为什么操作系统不用精确 LRU 做页面置换？* 精确 LRU 要求每次内存访问都更新时间戳或移动链表，硬件上做不到（不可能每次访存都陷入内核）。所以用 **Clock 算法**：给每页一个引用位，需要淘汰时转一圈，遇到引用位为 1 的清零继续转，遇到 0 就淘汰。这是 LRU 的低成本近似。
- *这个"近似"的思路重要吗？* 非常重要。工程里大量算法都是"精确版的廉价近似"：Clock 之于 LRU、布隆过滤器之于集合判断、HyperLogLog 之于精确计数。

**验证实验**：

```python
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, key):
        if key not in self.data:
            return -1
        self.data.move_to_end(key)          # 标记为"最近使用"
        return self.data[key]

    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)   # 淘汰最久未使用的

cache = LRUCache(2)
cache.put(1, 'a')
cache.put(2, 'b')
cache.get(1)
cache.put(3, 'c')          # 容量满了，淘汰 2
print(list(cache.data.items()))    # [(1, 'a'), (3, 'c')]
```

### 一致性哈希

**解决什么问题**：分布式缓存有 N 台机器，用 `hash(key) % N` 决定 key 归属。**一旦加一台机器，N 变了，几乎所有 key 的归属都变了**——缓存集体失效，请求全部压到数据库，可能直接把库打挂。

**追问链**：

- *一致性哈希怎么解决？* 把哈希空间首尾接成一个环，机器和 key 都映射到环上，每个 key 顺时针找到第一台机器。
- *加一台机器会迁移多少数据？* 只有落在新机器逆时针到上一台机器之间那段环上的 key 会迁移，期望是 1/N，而不是全部。
- *那数据倾斜怎么办？* 三台机器的哈希值可能很不均匀地落在环上，导致某台机器负责一大段。**虚拟节点**解决：每台物理机器在环上放几百个虚拟节点，位置就均匀了。
- *真实系统用的都是这个吗？* Redis Cluster 用的是**哈希槽**（16384 个槽位分配），不完全是一致性哈希，但目的一样：让扩容只影响局部。CDN 选节点、负载均衡都在用同样思想。

**验证实验**：

```python
import bisect
import hashlib

class ConsistentHash:
    def __init__(self, nodes=None, vnodes=200):
        self.vnodes = vnodes
        self.ring = {}
        self.sorted_keys = []
        for node in (nodes or []):
            self.add_node(node)

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add_node(self, node):
        for i in range(self.vnodes):
            h = self._hash(f'{node}#{i}')
            self.ring[h] = node
            bisect.insort(self.sorted_keys, h)

    def get_node(self, key):
        if not self.ring:
            return None
        idx = bisect.bisect(self.sorted_keys, self._hash(key))
        if idx == len(self.sorted_keys):
            idx = 0
        return self.ring[self.sorted_keys[idx]]

ch = ConsistentHash(['cache-a', 'cache-b', 'cache-c'])
before = {f'key{i}': ch.get_node(f'key{i}') for i in range(10_000)}
ch.add_node('cache-d')
moved = sum(1 for k, v in before.items() if ch.get_node(k) != v)
print(f'加 1 台机器，迁移 {moved} / 10000 = {moved / 100:.2f}%')
```

3 台变 4 台，迁移率应该在 25% 左右。**对比一下 `hash(key) % N`：那会迁移 75% 以上。**

### Merkle 树

**解决什么问题**：判断两份数据是否相同，而且要能回答"**哪里不同**"。逐个字节比对太慢，文件大到传不动时还希望"只传差异"。

**追问链**：

- *原理？* 把文件分块，每块算哈希作为叶子，两两向上再哈希，直到得到唯一的根哈希。根哈希就是整个文件的指纹。
- *为什么不直接用整文件哈希？* 整文件哈希只能回答"同不同"，回答不了"哪里不同"，而且必须把文件全部读完才能算出来。
- *谁在用？* Git（每个 commit 是一棵树）、IPFS、区块链、BitTorrent（分块校验），以及**网盘秒传和增量同步**。
- *为什么分块必须用"内容定义分块"（CDC）？* 如果用固定长度分块，在文件开头插入一个字节，后面所有块的边界全部错位，哈希全部失效，Merkle 树形同虚设。CDC 用滚动哈希按内容特征找边界，插入删除只影响局部。
- *这一条和秒传怎么连起来？* 见 1.12。

**验证实验**：

```python
import hashlib

def build_merkle(chunks):
    level = [hashlib.sha256(c.encode()).hexdigest() for c in chunks]
    tree = [level]
    while len(level) > 1:
        nxt = []
        for i in range(0, len(level), 2):
            left = level[i]
            right = level[i + 1] if i + 1 < len(level) else left
            nxt.append(hashlib.sha256((left + right).encode()).hexdigest())
        level = nxt
        tree.append(level)
    return level[0], tree

original = ['第一段内容', '第二段内容', '第三段内容', '第四段内容']
modified = ['第一段内容', '第二段内容', '第三段被改了', '第四段内容']

root1, tree1 = build_merkle(original)
root2, tree2 = build_merkle(modified)

print('根哈希相同?', root1 == root2)
print('各块是否相同:', [a == b for a, b in zip(tree1[0], tree2[0])])
```

你会看到根哈希不同，但**只有第三个块不同**。如果这是两个网盘客户端，它们只需要传第三个块——这就是"同名、前半段一样后半段不一样"只传差异的原理。
